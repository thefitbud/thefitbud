## Outcome
The QA seed always gives the slipping trainee a check-in they can start (so QT3's fill-and-send path always runs), and seeds a second trainer with their own client, so the staging smoke proves a trainer cannot read another trainer's real data.

## Context
- Source: the W3 report's "Follow-ups raised on 3 Nov" (`docs/specs/batches/W3.md`, 3 Nov continuation) and QA1's "Follow-ups raised" (`docs/specs/batches/QA1.md`); W3b is approved by Firoz, 3 Nov 2026 (`docs/specs/batches/W3b.md`). (QT2b and the review item on cross-trainer ownership).
- Today the seed guarantees a *submitted* check-in only; `apps/mobile/.maestro/flows/trainee/checkin.yaml:14-15` notes it does not guarantee a due or overdue one, so the fill path is conditional.
- `apps/api/qa-smoke/trainer.smoke.test.ts:95` asserts cross-trainer ownership with a nonexistent id (`00000000-...`), which proves only a 404 for nothing.
- New account: `qa+trainer2@thefitbud.com` (a QA alias, matches the redactor's allowlist `qa+[a-z0-9-]{1,32}@thefitbud.com`) with one client. Same password/OTP mechanism as the other QA accounts (QT2); **no new secret** — reuse `FITBUD_QA_PASSWORD` / `QA_TEST_OTP_CODE` by name. Reset must remove both trainers' data.
- Seed changes are applied by the nightly `seed-reset` job; this task runs no remote command.
