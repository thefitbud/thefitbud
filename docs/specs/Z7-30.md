## Outcome
Two account deletions that arrive together always answer one 200 and one 403 `ACCOUNT_ARCHIVED`, even when both read the same millisecond, and the concurrency test no longer flakes CI.

## Context
- Found 10 Nov 2026 during W7: `account.test.ts` > "archives once when two deletes arrive together …" failed intermittently on unrelated PRs with `expected [ 200, 200 ] to deeply equal [ 200, 403 ]`. Reproduce: `NOW=2026-11-10T10:00:00.000Z npx vitest run src/routes/account.test.ts -t "archives once"` in `apps/api`.
- Root cause: `POST /account/deletion` takes `now = nowIso()` (millisecond resolution). `archiveAccount` stores it as `archived_at` and afterwards decided "this call archived it" by `after.archivedAt === archivedAt`. When both requests read the same millisecond, the loser's guarded UPDATE changes nothing, but the stored `archived_at` equals its own `now`, so it also answered `archived`. No data damage (dates are not restamped; revokes and cancels skip rows already revoked or cancelled), but D-W6-35 requires the retry to get 403.
- Files owned by Z6-14 (W6); ownership for this fix: D-W7-14. Rules: D-W6-31, D-W6-35 in `docs/specs/batches/W6.md`.

## Gap list
- `archiveAccount` decides by timestamp equality instead of the batch result.
- The concurrency test does not pin the clock, so it only catches the race by chance, and it does not check the winner's revokes and cancels.
