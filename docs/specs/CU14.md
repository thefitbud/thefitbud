## Outcome
The assumption behind AB4's verbatim-`ApiClientError` branch is a written rule, so nobody adds a dynamic, data-bearing API error message that the mobile app would then show verbatim.

## Context
- Source: the W3 report's "Follow-ups raised on 3 Nov" (`docs/specs/batches/W3.md`, 3 Nov continuation) and QA1's "Follow-ups raised" (`docs/specs/batches/QA1.md`); W3b is approved by Firoz, 3 Nov 2026 (`docs/specs/batches/W3b.md`).
- **Corrected 3 Nov 2026 (D-W3b-7).** The original line here read "All 455 API error messages are static literals today"; both the count and the claim are wrong. `apps/api/src` has **773** `fail(` call sites, 750 quoted literals at the call site and 23 reached through an indirection — of which 22 resolve to literals and **one does not**: `apps/api/src/routes/notifications.ts:992` interpolates a retry window into the `NUDGE_LIMIT` / `NUDGE_RATE_LIMITED` message, which mobile shows verbatim under D-W3-12. AB4's verbatim rule therefore rests on a premise with one known exception. **D-W3b-7 resolved this on 3 Nov 2026 with option (b)**: the rule is written to permit a derived numeric value, so `notifications.ts:992` conforms and no code changes. The acceptance criteria below carry the decided wording.

## Acceptance criteria
- [ ] **Updated by D-W3b-7 (option (b), Firoz, 3 Nov 2026).** Firoz's wording is added **verbatim** to the `## API` bullet, immediately after "Stable domain error codes, one error body.":
      > API error messages must be static text, or static text with a derived numeric value such as a retry window. They must never include user data, IDs, or anything taken from the request, so clients can show them as-is.
