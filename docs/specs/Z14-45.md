## Outcome
A trainee on the last intake step taps **Submit intake** and the intake is sent. The app moves to the "waiting for your coach" screen (`waiting_review`), and stays there after a relaunch. If a submit fails, a friendly message with **Try again** stays on screen. The screen never goes blank, and no error is shown and then wiped. If a required question is empty, the trainee is taken to that question's step with a line under it.

## Context
- Firoz, staging build 6 (`4db3f45`), iOS, `vikram.onboarding@demo.fitbud.test`: tapping **Submit intake** shows a bare "Loading…" page, then the form again with a spinner on the button. The spinner then stops and the app stays on Intake, including after a relaunch. The trainee is stuck. The same code runs on Android.
- **Cause 1, out-of-date version (`IntakeScreen.tsx`).** On the last step, `goNext()` awaits `saveDraft()`. That save moves the server draft from version v to v+1, but `submit()` runs in the same render's closure and still reads `version === v`. `submit()` then saves the draft again with `expectedVersion: v`. The API (`apps/api/src/routes/onboarding.ts`, draft save) answers `409 ONBOARDING_VERSION_CONFLICT`, so `submitOnboarding` is never called. This happens on every tap and on every account.
- **Cause 2, the error is hidden.** The `submit()` catch sets the message and then awaits `load()`. `load()` starts with `setErrorMessage(null)` and `setLoading(true)`, so the whole screen becomes the "Loading…" text and the message is lost.
- The route comes from the server's onboarding status (`apps/mobile/src/navigation/resolveRoute.ts`). After a real submit, `refreshSession()` already routes to `waiting_review`; nothing in routing needs to change.
- **D-W14-44** (this fix), **D-W14-3** (error copy), **D-W14-4** (never wait for a human).
- No test covers `IntakeScreen` today.

## Acceptance criteria
- [ ] On the last step, one tap makes exactly one draft save, then one `submitOnboarding` call with `expectedVersion` equal to the version **that save returned**. Thread the returned version through: don't read React state that was set in the same handler.
- [ ] The submit idempotency key is reused on a retry of the same logical submit and replaced only after a success or a conflict reload (keep today's rule).
- [ ] After a successful submit, `refreshSession()` runs and the app routes to `waiting_review` (the existing flow).
- [ ] Before submitting, required questions are checked with the same rule the server uses (`required` plus an empty answer). If any is missing, no request is sent: the screen goes to the step holding the first missing question and shows "Answer this question to continue." under it. If the server still answers `ONBOARDING_INCOMPLETE`, do the same using `missingFieldIds` and `invalidFieldIds`.
- [ ] On `ONBOARDING_VERSION_CONFLICT`, answers and the version are refetched **without** the full-screen loading state (a background refetch). The trainee stays on the same step, and an ErrorBanner reads "Your answers were updated somewhere else. Check them and submit again." The banner is not cleared by the refetch.
- [ ] Offline or any other failure shows `userFacingMessage` copy, for example "You're offline. We'll retry when you're back." or "Something went wrong on our side. Try again.", in the ErrorBanner, with the footer button still usable as **Try again**. No raw codes, statuses or `err.message` (D-W14-3); details go through `reportError`.
- [ ] A draft save between steps keeps working; its conflict path uses the same background refetch and keeps its message.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.

## Decide-and-note
1. **Last-step save (recommended):** `goNext()` on the last step calls `submit()` only; `submit()` does the one draft save and passes the returned version on. Don't keep two saves.
2. **Where the conflict copy lives (recommended):** a small mapping in `IntakeScreen.tsx` for `ONBOARDING_VERSION_CONFLICT`. Everything else goes through `userFacingMessage`.
