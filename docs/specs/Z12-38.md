## Outcome
In-app notifications and toasts never get stuck: they show one at a time, leave on their own, can be swiped away, and a tap opens the right screen.

## Context
- Finding 8 (Firoz, 14 Nov): in-app notifications stay stuck on screen.
- Mocks: TR-06h, TM-13b (banners), TR-07b (undo toast), TR-26f (saved toast), TM-04m (sent toast). TR-26f's and TM-04m's screens are built by Z12-43 and Z12-50 on this queue.
- Keep `Snackbar`'s call signature so existing callers (`AttentionTab`, `ClientStatusScreen`, `DietTab`, …) need no change; the host mounts once at the root for both roles.

- `trainee/notifications/ForegroundBanner.tsx` and `InAppBanner` in `Surfaces.tsx` have no timer and no swipe gesture (ISSUE-MAP #8).

- Written against `main` at `3c227e12b`. Re-check each item on the latest `main` before building; drop what is done and say so in the PR (AGENTS.md).

- [ ] Toasts with an action (Undo, View) stay 6 s and dismiss on a tap outside.
- [ ] Works for trainee and trainer; the old trainee-only banner path is removed.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.
- [ ] **Device gate** (W12-PROMPT §3, D-W12-16) on the PR head: `ci`, `e2e` and `banned-strings` green; the Z12-35 device workflow ran this task's Maestro flows on the iOS simulator and the Android emulator, light and dark, as trainee and trainer, with zero crashes, red boxes or warnings in the device logs; the PR lists `screen ID → control → result` for every control on this task's screens; a screenshot of each mock ID in both themes on both platforms in `docs/qa/<ID>/`, and this task's rows in `docs/qa/W12/parity.md` filled; anything only a real phone can prove is added to Z12-58's Firoz checklist.
- [ ] Trigger a coach-note push with the app open (TR-06h) and on Clients (TM-13b): it leaves by itself in about 4 s; a swipe removes it; a tap lands on the right screen; two in a row queue and do not stack.
