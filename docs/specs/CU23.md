## Outcome
A trainee's week strip and "This week" rollup show day states derived from what they were actually assigned and actually did. No hardcoded or invented states anywhere on the path, and a shape mismatch between client and server fails loudly instead of silently degrading.

## Context
- Decision: **D-W3b-25** (`docs/specs/batches/W3b.md`), Firoz, 4 Nov 2026. Raised by CU13's review (#207).
- `GET /me/week` has **never been implemented**. `apps/api/src/routes/me-day.ts:155-180` touches no database: it answers seven consecutive dates all in `state: "future"`, whatever the trainee has done, and it derives those dates in **UTC** (`new Date().toISOString().slice(0,10)`, `:167`), not the trainee's zone.
- The client parses that response with `weekReadModelSchema` (`packages/api-client/src/stage1-augment.ts:332-338`), which requires `workouts`, `meals` and `todayNutrition`, so **every** call throws a `ZodError`.
- All three mobile call sites swallow it — `apps/mobile/src/trainee/TodayTab.tsx:195`, `TraineeDateNavigator.tsx:68`, `DietTab.tsx:205` — and the strip falls back to deriving state from the date alone: `future` ahead of today, **`missed` behind it** (`TraineeDateNavigator.tsx:89`). Nothing crashes, which is why it went unnoticed.
- **The read model already exists and is already served.** `apps/api/src/domain/week-read-model.ts:124` exports `buildWeekReadModel(db, { relationshipId, start, timeZone, nowIso })`, and `apps/api/src/routes/workspaces.ts:110-138` already serves it to trainers at `GET /workspaces/relationships/:rid/week`. **So this task is not "build a week read model"** — it is "serve the existing one to the trainee actor". Verified by the orchestrator on `main` at `0f80b63`.
- **No migration and no new indexes** (D-W3b-25's stop condition is therefore not triggered; see Stop conditions for when it would be). Every field is derivable from `workout_assignments` + `workout_executions` and `meal_assignments` + `meal_compliance`, and the composite indexes the 7-day range scan needs already ship: `workout_assignments_relationship_date_idx` and `meal_assignments_relationship_date_idx` on `(coaching_relationship_id, local_date)` (`apps/api/drizzle/0030_perf_indexes.sql:20-21`).

## The contract: what the screens read
D-W3b-25 says the screens decide the contract. The field-by-field audit is done; **the answer is that `weekReadModelSchema` already is the contract and nothing is removed from it.**

Read by the **mobile** Week UI — six fields:

| field | read at |
|---|---|
| `workouts.assigned`, `workouts.completed` | `TodayTab.tsx:666-667` |
| `meals.assigned`, `meals.logged` | `TodayTab.tsx:668-669` |
| `days[].date`, `days[].state` | `TraineeDateNavigator.tsx:82,88`; `DietTab.tsx:319,325`; `packages/ui-mobile/src/WeeklyConsistency.tsx:47-49` |

Read by **trainer web**, from the same builder — so these stay: `days[].workoutLabel`, `days[].mealsLogged`, `days[].mealsAssigned`, `days[].mealSlots`, `todayNutrition.*` (`apps/trainer-web/src/pages/ClientOverviewPage.tsx:81-93,283,388-390`).

Read by nobody: `start`. All three clients compute `startOfWeekMonday(selectedDate)` themselves. **Keep it** — removing it would change the trainer route's published response, which is outside this task, and it is the server's echo of which week it answered.

**Two corrections to the framing this task was briefed from.** `DietTab` has **no** "This week" rollup (`grep -n "This week" apps/mobile/src/trainee/DietTab.tsx` is empty); it reads only `.days`. And `WeeklyConsistency`'s `days` prop is typed as `{date, state}` only (`packages/ui-mobile/src/WeeklyConsistency.tsx:7-14`), so it structurally cannot read the richer per-day fields.

## Acceptance criteria
- [ ] `GET /me/week` resolves the trainee's own active relationship (the query already at `me-day.ts:62-71`, 404 `RELATIONSHIP_NOT_FOUND`), loads the trainee's timezone with `loadTraineeTimezone`, and returns `buildWeekReadModel(...)` parsed by `weekReadModelSchema`. **A trainer must not be able to reach another trainee's week through it**; role stays `["trainee"]` and the relationship comes from `actor.userId`, never from the request.
- [ ] `apps/api/src/routes/workspaces.ts:110-138` is the template; the **only** substitution is the relationship lookup. Do not fork or copy `buildWeekReadModel` — call it.
- [ ] Today is `formatLocalDate(now, timeZone)`, and the default `start` is Monday-aligned exactly as the trainer route does it (`workspaces.ts:126-130`). **The UTC `slice(0,10)` is gone.**
- [ ] `?start=` is validated with `localDateSchema` and a malformed value returns **400 with a stable domain error code**, not a 200 with echoed nonsense and not a 500. Today `?start=2026-11` returns 200, `?start=2026-02-30` returns 200 with dates rolling into March, and `?start=garbage` returns an unhandled-`RangeError` **500** (recorded in #207 and in `packages/contracts/src/me-week.ts:11-18`). Pick the existing error code used for malformed path/query dates elsewhere in the API rather than inventing one; if none exists, that is a stop condition.
- [ ] `packages/contracts/src/me-week.ts` is removed along with its `index.ts` export, and nothing still imports it.
- [ ] The three swallowed catches are gone: a failed or unparseable `/me/week` surfaces the real error to the user through the screens' existing error affordance. **It must not fall back to states derived from the date alone** — that fallback is the defect. Where a screen has no error affordance, show the "Weekly view isn't available yet" state from D-W3b-25 rather than inventing day states.
- [ ] The staging smoke parses `weekReadModelSchema` and asserts that a past day with a completed execution is **not** `future`.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.

## Stop conditions
- Any field the UI reads turns out to need a **migration or new indexes** (D-W3b-25: stop and report, Firoz decides separately). The audit above says it does not; if the implementer finds otherwise, that is the finding, not a reason to add one.
- No existing stable error code fits a malformed `?start=`, so a new one would have to be minted.
- Serving the real model changes what a **trainer** sees, i.e. the change cannot be made without touching `week-read-model.ts` or `workspaces.ts`.
- Removing a swallowed catch leaves a screen with no honest way to report the failure, and the "Weekly view isn't available yet" state would have to be designed rather than written as copy.
- A file outside `files_owned` must change.
- The task would need a remote command, a secret or a deploy.
