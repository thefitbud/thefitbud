## Outcome
A trainer with 200 clients, months of activity and many check-ins can scroll each list to the end; rows arrive a page at a time as they scroll, the first page paints at once from the cache, and nothing is cut off at 50.

## Context
- Diagnosis #18. **D-W14-26** (page size 30, prefetch at half a screen, footer states). D-W14-6 / Z14-3 (snapshot paint: the first page is the snapshot; later pages are not cached across launches).
- API: `GET /clients` and `GET /activity-feed` already page; Z14-20 adds the check-in inbox with `segment`.
- Every list today is a `.map()` inside `Screen`'s `ScrollView` (`components/Screen.tsx:71-131`), which cannot virtualise or report the end. `ListScreen` gives the same v3 chrome (safe area, header slot, pull to refresh, footer/toast slot) on a `FlatList`/`SectionList`, and is reused by Z14-22 (Attention) and Z14-24 (notes).
- Four screens: Clients (all chips and search), Activity, Check-ins (three segments), plus the name lookups.

## Acceptance criteria
- [ ] `ListScreen` matches `Screen`'s v3 look pixel for pixel at the top of the list (captures before/after), supports a list header, sticky section headers, pull to refresh, `onEndReached`, and exposes a ref with `scrollToOffset`/`scrollToLocation`.
- [ ] `usePagedList` holds items + `nextCursor`, loads the next page once at `onEndReachedThreshold` 0.5, never twice for the same cursor, resets on pull to refresh, chip, search or segment change, and drops a late page from an old query.
- [ ] Clients: 30 per page with the current chip and search; the second `listClients` call (`ClientsTab.tsx:352-353`) is gone (counts from Z14-1's clients list if merged; otherwise the existing count source, recorded).
- [ ] Activity: pages by scrolling; the "Load more" button goes (keep a "Load more" button only as the retry of a failed page).
- [ ] Check-ins: each segment pages with Z14-20's `segment`.
- [ ] Footer: a quiet "Loading more…" skeleton row while a page loads; on failure an inline row "Couldn't load more. Try again" (offline: "You're offline. Showing what's loaded." neutral, D-W14-9); nothing at the end of the list.
- [ ] Names-only lookups (`AttentionTab.tsx:216`, `MoreScreen.tsx:107`) no longer depend on the first 50 clients (use the Attention response's names and Z14-1's counts; record the choice).
- [ ] Android back on these tabs still follows D-W14-24; scroll position is kept when returning from a profile.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.

## Out of scope
- Product rules (AGENTS.md, never break): only the trainer resolves an exception; no auto-send (WhatsApp is a wa.me prefill the user sends); no percentages or streaks; dates read like "Wed 21 Oct", never ISO or raw enums; payments are tracking only; ended clients are read-only on server and UI.
- Error copy (D-W14-3): friendly copy only, never raw error codes, HTTP statuses, `err.message` or bracketed codes on screen; say what actually went wrong; keep a way forward. Map through `userFacingMessage`/`userFacingError`.
- Working rules: no remote or deploy commands; no secrets; one branch `claude/<ID>-<slug>`, one PR `<ID>: <summary>` off the latest `main`, updated by merging `main` (never rebase or force-push); never cancel an Actions run; never write the mention handle.
- Attention's layout (Z14-22) and the notes list (Z14-24).
