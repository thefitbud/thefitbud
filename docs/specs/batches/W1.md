## Decisions
- **D-W1-1 [change] Drop false dependencies.** Decided: yes to all three (Firoz, 30 Oct: "makes sense"; v14 D-B5).

- **D-W1-2 [change] Real sign-in needs a token exchange (new task AU1b).** Decided: Option A (v14 D-B6; decided by Claude on the recommendation, 31 Oct).
  - **The problem:** on `main`, `/auth/login` (and the OTP, reset and set-password routes) returns a *Firebase custom token* when `AUTH_MODE=firebase`. Both clients send that token straight back as the bearer token. AU1 makes the API verify *ID tokens*, so a custom token will fail, and nobody can sign in on staging even after AU1.
  - **Option A (recommended):** the API exchanges the custom token server-side through the Identity Toolkit REST API (`accounts:signInWithCustomToken`) and returns `idToken` + `refreshToken`. A new `POST /auth/refresh` calls the Secure Token API. Clients stay free of the Firebase SDK. It needs `FIREBASE_WEB_API_KEY`, which is a public key, as a var.
  - **Option B:** add the Firebase JS SDK to web and mobile and call `signInWithCustomToken` on the client.
  - Client-side storage and refresh (web + mobile) becomes **AU1c** in W2, because backend and UI never share a PR.
- **D-W1-3 Firebase projects** (Firoz, 30 Oct; v14 §6 step 2). Both on the Spark plan with Analytics off. Auth is initialized with no providers enabled. Each has a Web app and an Android app. Web API keys: see D-W1-8.
