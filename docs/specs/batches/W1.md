## Decisions needed before launch
- [ ] **D-W1-1 [change] Drop false dependencies.** Recommend yes to all three.
  - **I4a ← I2d:** wrangler envs don't need the library seed. The real ordering is I7 then I4a, because both edit `wrangler.toml`.
  - **X2 ← F4d:** X2 is build config (API URL, predev, svg pin). F4d is a post-beta diet UI fix.
  - **I2c ← I2e:** v13 already says that if this can go, I2e moves post-beta. The exercise emitter doesn't read the demo-seed food slugs.
- [ ] **D-W1-2 [change] Real sign-in needs a token exchange (new task AU1b).**
  - **The problem:** on `main`, `/auth/login` (and the OTP, reset and set-password routes) returns a *Firebase custom token* when `AUTH_MODE=firebase`. Both clients send that token straight back as the bearer token. AU1 makes the API verify *ID tokens*, so a custom token will fail, and nobody can sign in on staging even after AU1.
  - **Option A (recommended):** the API exchanges the custom token server-side through the Identity Toolkit REST API (`accounts:signInWithCustomToken`) and returns `idToken` + `refreshToken`. A new `POST /auth/refresh` calls the Secure Token API. Clients stay free of the Firebase SDK. It needs `FIREBASE_WEB_API_KEY`, which is a public key, as a var.
  - **Option B:** add the Firebase JS SDK to web and mobile and call `signInWithCustomToken` on the client.
  - Either way this is an auth-boundary change, so Agents.md requires Firoz's approval. Record it in the specs' `approvals`.
  - Client-side storage and refresh (web + mobile) becomes **AU1c** in W2, because backend and UI never share a PR.
- [ ] **D-W1-3 Firebase projects.** Confirm the staging and prod project IDs, and that email/password sign-in is enabled in both. The specs need the project IDs (not secrets).
- [ ] **D-W1-4 OTP channels for beta.** `/auth/otp/start` can send by email or WhatsApp. WhatsApp needs the Cloud API, an approved template and the `WA_*` secrets. Recommend **email-only OTP for beta**, with WhatsApp OTP post-beta.
- [ ] **D-W1-5 Concurrency.** One Max seat: **at most 3 implementer sessions at once**, plus short reviewer sessions. Confirm.

Decided for later batches (needed by W2, listed here so the bots can prepare the specs):
- **Email provider (I5):** ZeptoMail, Cloudflare Email Service or Resend. `types.ts` today allows `resend | ses` only, and `lib/email.ts` throws for anything other than `dev_sink` / `disabled`.
- **Push provider (X4) [change]:**
  - **Today on main:** the server's `fcm` mode is a stub that returns `fcm_not_configured`. Mobile registers a synthetic `local-test-fcm-…` token. **Trainees never register a device** (`AuthProvider.tsx` skips them), yet trainee reminders are the core push need.
  - **Recommendation: Expo Push Service.** `expo-notifications` is already installed. Expo handles APNs and FCM with credentials uploaded to EAS. The other route, FCM HTTP v1 direct, needs the Firebase iOS SDK to get FCM tokens on iOS.
  - **Split X4 into four tasks:** X4a server sender, X4b device registration for both roles, X4c reminder pushes end to end, X4d notification tap → deep link. **Live Activity (frames 27–27c) goes post-beta.**
- **Crash reporting (BT2):** Sentry (v13's suggestion) is a new provider, so it needs a recorded approval.

**Ownership clashes and how to avoid them:**
- `pnpm-lock.yaml`: AU1 adds `jose`; X2 pins `react-native-svg`. Whichever merges second merges `main` in and re-runs `pnpm install`. No other lockfile changes in W1.
- `apps/api/package.json`: only the infra lane edits it. If I2d needs a script flag, it adds it inside `library-seed.ts`, not in `package.json`.
- `apps/api/src/index.ts`: only I8 may touch the scheduled handler. Nobody else edits `index.ts` in W1.
- If any task needs a file another lane owns, it stops and asks (spec stop condition).
