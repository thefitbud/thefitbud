- **D-W3-8 Push delivery is at-most-once.** Decided by Firoz, 31 Oct 2026. When the provider has accepted a push but the write recording that acceptance fails, the queue retry must **not** send again: mark the attempt before calling the provider, and on a retry whose outcome is unknown record it as uncertain instead of resending. Chosen over at-least-once, so a trainee is never sent the same reminder twice; the cost is that a reminder can rarely be lost. Matches "dedupe before delivery" and "record provider acceptance separately from completion" in AGENTS.md. Why it is needed: on `main` today `deliverReminderMessage` skips a redelivery only when `providerStatus` is already `accepted`, which is exactly the write that failed, so the queue's `message.retry()` sends the push a second time (confirmed in the pre-W3 check, 31 Oct, and recorded as a W2 follow-up). The fix needs an attempt marker written before the provider call, so it carries a migration and cannot ride along in a copy or UI PR. Whichever push-api spec takes it (X4c or a new id) owns `apps/api/src/domain/reminders.ts`, `apps/api/src/jobs/reminders.ts` and that migration. **Task:** X4i (M, opus, reminders lane: X4c → X4i → X4f → X4h), decided by Firoz, 1 Nov 2026.
- **D-W3-9 Push token held by another user. Decided by Firoz, 2 Nov 2026:** when an authenticated user registers an Expo push token that currently belongs to another user, the API **always** reassigns the token to the new user, whether the old row is `active` or `revoked`. A new sign-in registering the token means the previous user is treated as signed out on that device: their row is released or revoked and they stop getting pushes there. There is **no** 403 for a foreign token. This also covers the constant token used in `AUTH_MODE=test`. The option "refuse only an active foreign row" was **not** chosen. Why: an Expo token belongs to the installation, so every FitBud user of one phone reports the same token, and `routes/notifications.ts:183` answered `403 DEVICE_TOKEN_OWNED` to the second user with no status condition, which blocked the "Done when" line "a trainee and a trainer register real Expo tokens". **Task:** X4k (S, opus, reminders lane, after X4h). Supersedes X4b's 403 criterion.
- **D-W3-10 BT3 ships with draft legal copy. Decided by Firoz, 2 Nov 2026:** counsel's text is still being drafted, so BT3 builds the public Privacy, Terms and Credits pages **now**, with the Privacy and Terms bodies marked as drafts and no invented legal prose. This **overrides BT3's acceptance criterion 2** ("no placeholder text ships (if counsel's text is missing, stop)") and clears BT3's blocked row, which D-W3-4 had made conditional on `docs/legal/*.md` existing. Consequences, recorded in #133: the pages **must not reach production or store review** until counsel's text replaces the drafts (follow-up **BT3c**, manual step 4, due Mon 9 Nov), and **BT1 (W4) store submission is gated on that swap**, because store review needs live legal URLs. Credits is real content from `docs/spec/credits-and-licences.md` and the library `ATTRIBUTION.md`, not a draft. Note `placeholder` is itself a banned string at error severity (`docs/spec/banned-strings.json:62`), so the pages read "Draft". Used by BT3 (#133), BT3b (#144).
- **D-W3-11 Native session persists in SecureStore. Decided by Firoz, 3 Nov 2026:** supersedes D-W2-13. On Android and iOS the refresh token and minimal session metadata are stored with `expo-secure-store` (never AsyncStorage) so a session survives app kill, restart and Android back; only Sign out, a definitive refresh refusal or account deletion signs the user out, and a network error never does. Allowed exception to "no new dependencies in W3": `expo-secure-store` (needs a new EAS development build). **Task:** AB3.
- **D-W3-12 No misleading catch. Decided by Firoz, 3 Nov 2026:** no `catch` may show a message that names a cause it did not check. Auth: "That code didn't work" only for `OTP_INVALID`/`OTP_EXPIRED` (QT9's wording stays as written, D-QA1-11); other failures show a distinct message with a short error code and log name, message and zod issue paths in dev. Also: the mobile dev loop must not bundle stale `packages/*/dist`, and dev builds show the JS commit. **Task:** AB4 (after QT9).
- **D-W3-5 Live Activity outbox operation. Decided by Firoz, 1 Nov 2026: (a)**, LA2 maps `workout.log_set` to `workout.complete_set`; no API change.
- **D-W3-13 Android rest notification: countdown only. Decided by Firoz, 3 Nov 2026 (option A):** the rest state uses only the system chronometer countdown (`setUsesChronometer` + `setChronometerCountDown`). No progress bar, no stepped bar, no foreground service. A notification bar can't follow a clock without reposts, and those need throttled alarms or a battery-costly foreground service. `27-android-rest.png` and its HTML were updated to remove the bar. Used by LA3e.

- **D-W3-17 The trainer "Open FitBud on web" row opens the browser rather than copying the link.** Raised by BT3d, 3 Nov 2026, as a deviation from `ds5-ios-trainer-more-legal.png`, which shows a copy icon and "Copies the link for your laptop". BT3d therefore keeps the existing behaviour, reading "Opens in your browser" with the open-in-browser icon, because a copy icon over an action that opens a browser would mislead — a worse outcome than the deviation. **Accepted by Firoz, 3 Nov 2026:** keep the open-the-link behaviour; no clipboard follow-up. The frame's copy icon and "Copies the link for your laptop" are superseded for this row, so this is a standing deviation rather than outstanding work — do not re-raise it, and do not add `expo-clipboard` for it later. Used by BT3d.
- **D-W3-18 AB4 may add a ZodError branch on the login-code path.** Recorded by the orchestrator, 3 Nov 2026, after AB4's review found the task did not fix the incident it was written for. The 3 Nov incident happened in `verifyCode` on the login-code screen, and that path never reaches AB4's new mapper: `verifyCodeErrorFlow.ts:37-40` routes to QT9's `verifyCodeError`, where a `ZodError` is not an `ApiClientError` and falls through to the network copy — so a stale-`dist` parse failure still blames connectivity, with no error code and no dev log of the failing field paths.   AB4's own acceptance criterion 3 says "a ZodError **on any auth path**", and D-W3-12 requires a short error code plus zod issue paths in dev, so the spec already required this; its `files_owned` list simply did not anticipate the two QT9 files. Control flow is otherwise unchanged.
  **D-QA1-11 is not weakened.** It protects QT9's approved wording; a new branch for a case that previously fell through to the network copy changes no existing string. The AUTH-PARSE copy comes from D-W3-12.
  Precedent: D-W3-16 amended `files_owned` the same way when an approved frame forced a change to another task's test. Used by AB4.
