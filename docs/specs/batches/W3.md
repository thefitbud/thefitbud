- **D-W3-8 Push delivery is at-most-once.** Decided by Firoz, 31 Oct 2026. When the provider has accepted a push but the write recording that acceptance fails, the queue retry must **not** send again: mark the attempt before calling the provider, and on a retry whose outcome is unknown record it as uncertain instead of resending. Chosen over at-least-once, so a trainee is never sent the same reminder twice; the cost is that a reminder can rarely be lost. Matches "dedupe before delivery" and "record provider acceptance separately from completion" in AGENTS.md. Why it is needed: on `main` today `deliverReminderMessage` skips a redelivery only when `providerStatus` is already `accepted`, which is exactly the write that failed, so the queue's `message.retry()` sends the push a second time (confirmed in the pre-W3 check, 31 Oct, and recorded as a W2 follow-up). The fix needs an attempt marker written before the provider call, so it carries a migration and cannot ride along in a copy or UI PR. Whichever push-api spec takes it (X4c or a new id) owns `apps/api/src/domain/reminders.ts`, `apps/api/src/jobs/reminders.ts` and that migration. **Task:** X4i (M, opus, reminders lane: X4c → X4i → X4f → X4h), decided by Firoz, 1 Nov 2026.

### Decisions needed
- **D-W3-9 — can a revoked device-token row owned by another user be reclaimed?** `routes/notifications.ts:183` refuses a token held by a different `userId` **with no status condition**, and `DELETE` only sets `status: "revoked"` without releasing the token. An Expo push token is per installation, so it is the same token for every user of a phone — and in `AUTH_MODE=test` the token and installation id are literal constants for every user (`routing.ts:125`). So: trainer signs out → trainee signs in on the same build → `403 DEVICE_TOKEN_OWNED`, swallowed silently, no device row, no push, no message to the user. **This blocks the "Done when" line "a trainee and a trainer register real Expo tokens".** Options: 403 only for an `active` foreign row and reclaim a revoked one (recommended, task **X4k**); scope tokens per user (needs a migration); or accept one FitBud user per phone for the beta. The test-mode constant should become per-user either way.
- **LA2c — the iOS widget App Group fix (conflict 8), still unowned.** `@bacons/apple-targets` 0.2.1 ignores the target's `infoPlist`, so the widget reads `FitBudAppGroup` as nil and writes its rows where the app cannot read them. **LA2's entire device checklist (steps 2–7) cannot pass until this lands**, however correct the merged JS is. It needs `apps/mobile/targets/FitBudLiveActivity/**` or the iOS half of `plugins/withLiveActivity.js`; **no W3 spec owns either**, so it was reported rather than absorbed into LA3 (whose ownership is the Android half only).

### What the reviews caught that green tests did not
Every code PR needed exactly one fix round. In five of them a passing test suite was concealing a real defect, which is the main evidence that the fresh-reviewer rule is doing work under "no human code review":
- **X4b:** `notification_deliveries` references `device_tokens` with **no `ON DELETE`**, so hard-deleting a superseded row raised `FOREIGN KEY constraint failed` → a permanent 500 in exactly the reinstall case the task existed for. The test passed only because its fixture had no delivery row. Now soft-revokes onto a sentinel.
- **LA2:** the dedupe key included a row position that shifted after a partial clear, so **one set got two idempotency keys**. Also, a row kept from one workout could later be logged against a *different* workout, and a duplicate exercise name guessed the wrong occurrence.
- **X4c:** the visible lock-screen **body was unasserted** — injecting a meal name and entity id into it passed all 8 tests. "Push payloads carry routing only" was proven for the data keys but not for the text a stranger can read off a locked phone.
- **LA3b:** removing the iOS-only gate exposed a chain where Android's `restState` reports `running` but no `restEndsAt`, so `hasRest()` returned `false` — which the session reads as *"the trainee tapped Skip"*, firing on every app foreground and **wiping the in-app rest countdown**. The existing test asserted `false` there, pinning the defect. The fix cannot key on field presence: iOS also omits `restEndsAt` when rest genuinely ends, and that omission *is* the skip signal.
- **X4i:** `postJson` collapses timeout, abort, reset, non-2xx and unparseable JSON into `provider_error`, indistinguishable from a refusal, and the failure branch cleared the attempt marker as though the provider had answered. The reviewer **reproduced an actual double send**, and the PR's own test asserted it as correct. The marker is now freed only for categories that prove the provider answered.
- **X4f:** dedupe detection **matched a regex against the driver's error message**, provable only against the `node:sqlite` test harness. Had real D1's wording differed, an ordinary dedupe would have 500'd — reproduced on the second `PUT /me/meal-times` inside the 15-minute merge window, with a blast radius across `plans.ts`, `checkins.ts`, `relationships.ts` and `trainer-note-share.ts`, none of which X4f owns. Replaced with a structural `onConflictDoNothing`.
- **X4h:** the trainer event was stored *after* the idempotency record, so a crash in that window left a retry hitting a cached 200 with no event — the trainer never learning a check-in was submitted. Swapped; no cost, because the unique dedupe key already makes the insert idempotent.
