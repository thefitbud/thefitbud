- **D-W6-10 Day-state rules (FitBud UI, 6 Nov 2026; Firoz delegated: "decide what would make a user stay consistent … lock it with proper validation"):** (1) unlogged today (planned work, nothing logged, window open) is a new state `due`, not `partial` — partial means started and not finished, and a blank morning should feel open, not half-failed (v3 Today frames already separate empty vs partial, Z9-1); `due` comes from assignments + no observations + open window, never from the date alone (CU23). (2) A skip still counts toward `done`; item status stays `skipped`; never auto-skip. (3) A past day with real progress (`started`, or anything logged) is `partial`, not `missed`; `missed` is only a past day with planned work and no logs. (4) Unchanged: no planned work → `rest` (`future` after today); later assigned days → `future`; all closed (completed/modified/skipped) → `done`; closed window with nothing logged → `missed`; today started-not-finished → `partial`. `deriveWeekDayFromWorkouts` stays the only derivation. Implemented and validated by Z6-22.
- **D-W6-11 Plan status label (Firoz, 6 Nov 2026):** `plan_version_status.effective` displays as **Active** (frame 150); the enum stays `effective`; "Effective from/to/since" date phrases are unchanged. Z6-23.

- **D-W6-15 The Z5-4 scaffold test shrinks lane by lane (recorded by the orchestrator, 6 Nov 2026):** `apps/api/src/routes/w6-scaffold.test.ts` asserts every W6 mount answers 404 `not_implemented`, so it must fail once a lane replaces its stub router. Each lane that replaces a scaffold router (Z6-5 `/strength`, Z6-8 `/client-settings`, Z6-9 `/steps`, Z6-10 `/exceptions/bulk`, Z6-14 `/account`) removes **only its own mount** from that test's `MOUNTS` (Z6-10 also turns the "/exceptions/bulk is matched before /exceptions" case into a check that `/exceptions/bulk/resolve` reaches the real router while `/exceptions` is unchanged), and merges `main` before its own merge. The edits are disjoint lines made at different times; this is the one shared-file exception to D-W6-2. Also for Z6-10: undo is logged as a receipt in `idempotency_records`, not an `exception_actions` row, because that table's CHECK allows only acknowledge/resolve and a migration is outside the exceptions lane; the compatible types for D11 "missed workout, missed meal, missed log" are `missed_workout`, `skipped_workout`, `overdue_meal`, `skipped_meal`, `meal_logged_later`, `overdue_checkin` (not `meal_deviation`). Bulk resolve may take an item that is not yet reviewed straight to resolved (one step, as the web drawer does for a single Resolve), but it then writes the same `acknowledge` action and intervention that Mark reviewed writes, so history never shows a review time without a review action.

- **D-W6-16 Z6-11 test fixtures (recorded by the orchestrator, 6 Nov 2026):** the new log-time bounds made existing fixtures that logged tomorrow's meal or a not-yet-open workout fail. Z6-11 moved them to realistic times instead of loosening the rule, and added route tests, in `apps/api/src/routes/meals.test.ts`, `workouts.test.ts` and `notifications.test.ts` (test files only, outside its list). No other W6 lane owns them. Accepted after the fact; the logging lane's later tasks (Z6-12, Z6-15, Z6-19) merge `main` before touching them.

- **D-W6-17 How Z6-2 makes new assignments use v2, and v2's field shape (recorded by the orchestrator, 6 Nov 2026):** a migration alone cannot meet Z6-2's criterion "assignments created after the migration reference v2", because the fallback pin is the core constant `GLOBAL_CHECKIN_FORM_VERSION_ID` (v1) used by `resolveCheckinFormPin` in `apps/api/src/routes/checkins.ts`. Z6-2's `files_owned` is widened to `packages/core/src/checkin.ts` (a v2 version id constant and v2 field list; the default for new assignments becomes v2; v1 constants stay for history), `packages/core/src/index.ts` (export those only), `apps/api/src/routes/checkins.ts` (the fallback sites only), and seed/test files whose fixtures assume new assignments get v1 (updated to the spec's behaviour, never weakened). Schedules that explicitly pin a version keep it; no existing row is rewritten. **v2 field shape:** each field keeps the current `checkinFieldDefinitionSchema` shape and adds `key`; for standard questions `id` equals `key`. Types: `weight` measurement `body_weight_kg`; `waist`/`hips`/`chest` measurement `waist_cm`/`hip_cm`/`chest_cm`; `arm`/`thigh` measurement `other` with unit `cm`; `photo_front`/`photo_side`/`photo_back` photo_intent with their slots; `energy`/`sleep_quality`/`stress`/`hunger` `scale_1_5`; `notes` long_text; all optional (any required-answer rule that names a v1-only field such as `wellbeing` must apply to v1 only). The current parser strips unknown properties rather than rejecting them, so `key` is safe before Z6-6 adds it to the typed schema. Z6-6 (after Z6-2) also touches `packages/core/src/index.ts`; it merges `main` first.
