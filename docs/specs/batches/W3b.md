- **D-W3b-7 CU14's premise is false: one API error message interpolates a value. DECIDED — option (b), decided by Firoz, 3 Nov 2026.** Raised OPEN by the orchestrator the same day (#185) after CU14 audited the premise before editing `AGENTS.md` and stopped; Firoz chose option (b) and supplied the wording. **Resolution, in his words, to be added verbatim to `AGENTS.md`'s `## API` bullet:**
  > API error messages must be static text, or static text with a derived numeric value such as a retry window. They must never include user data, IDs, or anything taken from the request, so clients can show them as-is.

  **No code change follows.** `apps/api/src/routes/notifications.ts:992` already conforms: `retryMins` is a derived numeric value, which this wording permits, so the `NUDGE_LIMIT` / `NUDGE_RATE_LIMITED` message stays as it is and mobile keeps showing "in N min". There is no fix task, and no later task may "correct" that line on the strength of the old absolute reading. CU14 adds the sentences and cites `(D-W3-12, D-W3b-7)`; nothing else in `AGENTS.md` changes.

  The audit that forced the decision is below and stands as the record of what `main` actually contains.
  `docs/specs/CU14.md` Context says "All 455 API error messages are static literals today", and that is the entire basis for the rule it asks to write. Both halves are wrong. The orchestrator verified each claim below directly against `main` at `cd8d6d8`, independently of CU14's report.
  - **The count is 773, not 455.** `apps/api` has one error-envelope constructor, `fail(c, status, code, message, details?)` (`apps/api/src/lib/envelope.ts`); there are **773** `fail(` occurrences under `apps/api/src`, 750 of them a quoted literal at the call site (293 distinct strings) and 23 reached through an indirection or a ternary. CU14 hand-traced all 23; **22 resolve to static literals** (`knownProviderFailure`; `LibrarySnapshotFailure` and `LibraryPrescriptionError` in `apps/api/src/domain/library-snapshots.ts` and `packages/core/src/{nutrition,template}.ts`; `resolveAssignmentWindow` in `packages/core/src/schedule.ts`; `resolveCheckinFormPin`; `GENERIC_AUTH_FAIL`; `passwordRequirementMessage`).
  - **The 23rd is a real counterexample.** `apps/api/src/routes/notifications.ts:992` returns `` `You can nudge again in ${retryMins} min` `` on the `NUDGE_LIMIT` / `NUDGE_RATE_LIMITED` 429, where `retryMins = Math.max(1, Math.ceil(retryAfter / 60))`. Under D-W3-12 the mobile app shows an `ApiClientError` message verbatim, so this interpolated value reaches a user today. It is deliberate, merged code, and the same value is **also** returned in `details.retryAfter`; `apps/trainer-web/src/components/ExceptionDrawer.tsx:567-578` ignores `err.message` here and recomputes the string from `details.retryAfter`, so **web already complies** and a fix is a no-op for web — mobile is the only consumer that would change.
  Writing CU14's sentence as originally specified would have documented something untrue of `main` and put a merged, deliberate code path in violation with no task to fix it. Three ways out were put to Firoz; **(b) was chosen**, and the two rejected options are recorded so they are not reopened:
  - **(a) Fix first, then document** — rejected. A new task would make the message static and teach mobile to render `details.retryAfter`. Purist, but it adds mobile scope to a cleanup batch and, until mobile is taught, makes a mobile error message *less* useful (the user loses "in N min").
  - **(b) State the rule as it actually is — CHOSEN** (orchestrator's recommendation, Firoz's wording). The rule's purpose is that a client can show an API message verbatim without leaking data or lying; a derived numeric retry window does neither. True of `main` today, keeps AB4's licence intact, still forbids what the rule exists to forbid. It is a narrower rule than D-W3-12's reading implied, which is why it needed Firoz rather than the orchestrator.
  - **(c) Grandfather the one exception** — rejected. Smallest and honest, but it would leave rule and code in stated contradiction, inviting the next agent to "fix" `notifications.ts:992` without a decision.
  `docs/specs/CU14.md`'s Context line was corrected with #185 (455 → 773; "all static" → one documented exception), and its acceptance criteria are updated with this decision, since a spec is meant to be self-contained and this premise is the whole task. Used by CU14.
