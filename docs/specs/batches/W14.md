## Decisions

Firoz starts a task by pasting its prompt from `W14-prompts.md` or saying "start batch W14 task N". Each session carries its task end to end: re-check the spec against `main`, build, open the PR, get a fresh Opus reviewer subagent, fix what it confirms (one round), merge under the standing authorization (AGENTS.md), and append its row to this file's Report. A session may run several tasks in a row when Firoz asks. Decided by Firoz, 23 Nov 2026; format by FitBud UI.
- **D-W14-3 Error copy (standing for W14 and after).** (a) Friendly copy only: never show raw error codes, HTTP statuses, stack text, `err.message`, or bracketed support codes such as "(WO-SAVE)" or "(AUTH-NET)" on any screen; keep the code in `reportError`/Sentry tags instead. (b) An error says what actually went wrong and only what was checked (AGENTS.md "No misleading catch"): offline says offline, a refusal says what was refused, a server failure says it was on our side. (c) Every failure keeps a way forward (Try again, Back, or what to do). Map through `userFacingMessage`/`userFacingError`. Decided by Firoz, 24 Nov 2026 (via FitBud UI).
- **D-W14-4 Never wait for a human.** Agents do not stop to ask Firoz or Lokesh mid-task; they take their recommended option and record the question, the option and the reason in the PR and the Report (AGENTS.md "Decide and note"). The hard stops in AGENTS.md still apply. Firoz, 7 and 12 Nov 2026 (carried).
- **D-W14-5 Checks and device runs.** Required checks before merge: `ci`, `e2e` and `banned-strings`, green on the latest head. Mobile tasks: cheap checks and the Expo-web screenshot check first, then **one scoped device run: the task's changed screens plus the `launch` smoke** (D-W12-34 carried), dispatched as `gh workflow run device.yml -f flows=launch,<task flows>`; if the session cannot dispatch it, record the exact command in the PR and the Report and continue. **Never cancel or force-cancel an Actions run.** Firoz, 12 and 15 Nov 2026 (carried).
- **D-W14-6 One app, two data policies.** Trainee is **offline-first**: every trainee screen paints from the device store (persisted snapshots of day, week, workouts, progress, plan) with the outbox applied on top, refreshes in the background, and a log returns as soon as the local write lands; the push runs behind it and never blocks the UI. Trainer is **online-first with instant paint**: the last answer per screen is kept (memory + device) and shown at once while a refresh runs; trainer writes stay online with optimistic UI and Undo; no trainer outbox. Chosen by FitBud UI over two apps or full offline for trainers (trainer actions resolve exceptions and need the live server state), 24 Nov 2026.
- **D-W14-7 Device store is expo-sqlite.** The outbox and the trainee read snapshots move from SecureStore chunks to `expo-sqlite` (its key-value store or one table), behind the existing `AsyncKeyValue` interface (`apps/mobile/src/sync/storage.ts`). SecureStore keeps tokens only. Existing outbox rows are migrated on first launch and never dropped. This is the Z12-57 "swap the adapter for a database" step. Native change: one EAS build pair after Z14-5 (Firoz). FitBud UI, 24 Nov 2026.
- **D-W14-8 Needs you reads stored exceptions.** Exception evaluation leaves the read path: it runs after the writes that can change it and in the existing cron; `GET /exceptions/attention` reads stored rows, and may re-evaluate only relationships whose last evaluation is older than 15 minutes, in one batched pass. No auto-resolve (AGENTS.md product rules). Target: at most 12 D1 queries for 21 clients, flat in the number of clients. FitBud UI, 24 Nov 2026, from FitBud Tech's measurement.
- **D-W14-9 Offline is neutral.** Offline uses the TR-06e / TR-07d neutral banner (wifi-off, neutral fill, no alert role) and the sync chip; crit is only for real failures (TR-06g). FitBud UI, 24 Nov 2026, from the approved v3 frames.
- **D-W14-10 Session RPE and the summary.** After every finish the summary (W-17a) asks for session RPE, optional unless the plan requires it, and the trainee can set or change RPE on their own completed workout for 48 hours (new endpoint). "View summary" on an already-finished workout opens a read-only summary with Done, never "Save and share" again. FitBud UI, 24 Nov 2026; layout waits on D-W14-14.
- **D-W14-11 Meal photo is real.** Camera and Gallery open `expo-image-picker`; the image is resized to at most 1600 px on the long edge, JPEG ~0.7, uploaded through the existing media upload, and attached to the logged meal by a new endpoint. Failures are shown (D-W14-3), never swallowed. FitBud UI, 24 Nov 2026.
- **D-W14-12 Live workout outside the app.** iOS: `LogSetIntent` is compiled into the app target as well as the widget, and the native module emits an event when the intent appends a row, so a running app drains it at once (otherwise on the next foreground, as today); a row for a workout that has already finished is dropped with a note in the sync status, never sent. Android adopts the iOS TR-15d layout ("Log {target}" and "Open", no ± steppers) on its own **"Live workout"** channel (IMPORTANCE_DEFAULT, silent, only-alert-once, ongoing, VISIBILITY_PUBLIC, CATEGORY_WORKOUT), separate from "Workout reminders". No foreground service in W14 (it needs a Play health-service declaration; follow-up if the lock screen still hides it). FitBud UI, 24 Nov 2026.
- **D-W14-13 Pushes pop up.** Android reminder and coach channels are recreated as new IDs with IMPORTANCE_HIGH (`workout_v2`, `meal_v2`, `checkin_v2`, `coach_v2`, `plan_v2`, `account_v2`, `clients_v2`; `summary` stays DEFAULT), because Android never raises an existing channel's importance; the old IDs are deleted on first launch. The server sends `channelId` (the v2 id for the push group) and `priority: "high"`. Risk accepted: an Android build older than the Z14-6 build may not have the v2 channels; staging has no production users and every tester gets the new build (Z14-4 records how expo-notifications handles an unknown channel). The app sets a foreground handler that shows the banner, re-reads permission on return to the app, and re-registers the token when permission turns on. FitBud UI, 24 Nov 2026.
- **D-W14-14 W14 mocks approved. Open.** Z14-10 draws the mocks for the post-workout summary with RPE and its read-only state, the time-zone list, the assigned diet plan, and the diet "something different" states. Firoz reviews them. **Z14-12, Z14-13 and Z14-14 stop and report until this line reads "Approved by Firoz, <date>"**; every other task runs. FitBud UI updates this line when Firoz approves.
- **D-W14-15 "Nudge" becomes "Remind".** Trainer action label "Remind", confirmation "Reminder sent", trainee push title "{Coach} sent you a reminder", inbox row "Reminder from {Coach}". Chosen over "Notify" (Firoz's first suggestion) because "notify" says how, not what, and reads like a setting; API types (`activity_nudge`, routes) keep their names. FitBud UI, 24 Nov 2026. **Confirmed by Firoz, 24 Nov 2026** ("Remind" replaces "Nudge").

Saves `traineeTimezone` as today. FitBud UI, 24 Nov 2026; layout per D-W14-14.
