## Outcome
A trainer can set, for one client, the name FitBud shows them by and a contact phone, stored on that coaching relationship only. The client's sign-in number and their own profile name never change.

## Context
- Product direction: Firoz, 7 Nov 2026 (D-W6-42). Background: D-W6-25 (1) (why `/basic` was moved out of Z6-8), D-W6-34 (b) (the trainer-owned fields on the relationship).
- **Migration + API only, no screens.** The Client settings screens (frames 209, 210) are W8. Frame 210 is context for the two fields only: "Name" and "Phone · WhatsApp". Its other fields (email, date of birth, sex, height, city, time zone) are not part of this task. Frame 209 says goal and coaching details live in Plan › Coaching setup.
- **New columns on `coaching_relationships`**, both nullable: a trainer-set display name (for example `trainer_display_name`, trimmed, 1–120 characters, the same bound as display names elsewhere) and a contact phone (for example `contact_phone_e164`). NULL means "not set". Add a CHECK for each where SQLite's `ADD COLUMN` allows it; otherwise enforce in the API only and say which in the PR.
- **Phone validation follows the existing rule.** Contract: `z.string().trim().min(8).max(20).nullable()`, as `updateTrainerProfileRequestSchema.whatsappE164` in `packages/contracts/src/profile.ts`. Server: normalise with core `normalizeWhatsappE164` and store `+<digits>`, as the trainer profile update does (`meRoutes.put("/trainer-profile")`, `apps/api/src/routes/auth.ts:308-315`); a number that does not normalise answers 400 with a static message. The phone never appears in logs, errors or analytics.
- **Never write `user_identities.mobile_e164`** (the trainee's OTP sign-in identifier) and **never overwrite `trainee_profiles.display_name`** (the trainee's own name, shared across relationships). The PATCH reads and writes `coaching_relationships` only.
- **Goal stays in Coaching setup** (`coaching_configurations`, frames 209 and 210, DECISIONS-21OCT item 2). No goal field in this task.
- **`PATCH /client-settings/relationships/:id/basic`**: body has `displayName` and `contactPhone`, each optional and nullable (null clears it; at least one present). Owner trainer only: another trainer, the trainee or an unrelated user get the same answer as the other client-settings writes. Ended relationship → 409 `RELATIONSHIP_ENDED`. Requires `Idempotency-Key`, using the module's existing idempotency helper (replay returns the stored answer; a reused key with a different body answers 409). Errors are static text (D-W3-12, D-W3b-7). It replaces the `not_implemented` catch-all for this path; other unknown paths keep the static 404.
- **`GET`** returns the two new values in `basics` (null when unset) next to the existing `displayName` and `phoneE164`, which stay as they are (the trainee's profile name and sign-in phone, read only). Recommended default (D-W6-34): the API returns both and does not merge them; which one a screen shows is W8's choice. Using the trainer-set name on Home, Clients and WhatsApp drafts (frame 210's helper text) is later UI work, not this task.
- **Migration number:** the next free number in `apps/api/drizzle/meta/_journal.json` at merge (0040 if nothing lands first), serial with other migrations. Z6-2's parked migration (#270, written as 0036) also needs a number: whichever merges first takes the next free one and the other merges `main` and renumbers its own migration (AGENTS.md; D-W6-42). Never edit a merged migration. The migration-lane files (`schema.ts`, `drizzle/**`, `migration-chain.test.ts`) pass between Z6-8b and Z6-2 one at a time, as D-W6-24 did for `ownership.ts`. Remote application is a manual step after merge.
- **Account purge (Z6-17, D-W6-39) must clear the new columns.** Z6-8b updates `apps/api/src/jobs/account-purge.ts`: when a trainee is purged, every relationship where they are the trainee gets the name set to "Deleted user" (`DELETED_USER_NAME`) and the contact phone set to NULL; when a trainer is purged, both columns are set to NULL on their relationships (recommended default, D-W6-34: the trainer's copy of a client's details has no use once the trainer is gone, and the client's own data is untouched). The trainer-set names and contact phones of a purged trainee are added to the values the free-text scrub removes (`loadPersonValues`), like invitation names are today. Statements join the existing guarded batch.
- `apps/api/src/seed/qa/ownership.ts`: change only if its tests need the new columns listed; the columns are not foreign keys, so probably no change.

## Acceptance criteria
- [ ] A new migration adds the two nullable columns to `coaching_relationships`; it is additive (no table rebuild, no data rewrite) and the migration chain test passes from empty and from a seeded database.
- [ ] `PATCH …/basic` with a name and a phone stores both on the relationship and returns the updated settings; `GET` returns them in `basics`.
- [ ] `null` clears a value; an empty body, a blank name, a name over 120 characters or a phone that does not normalise answers 400 with a static message.
- [ ] Another trainer, the trainee and an unrelated user cannot read or write (same status as the other client-settings routes); ended → 409 `RELATIONSHIP_ENDED`; reads of an ended relationship still work.
- [ ] Missing `Idempotency-Key` → 400; a replay returns the stored answer without a second write; a reused key with a different body → 409.
- [ ] After a PATCH, `user_identities.mobile_e164` and `trainee_profiles.display_name` are unchanged (asserted on the rows).
- [ ] No goal field exists in the request, response or migration.
- [ ] The account purge sets the name to "Deleted user" and the phone to NULL on a purged trainee's relationships, sets both to NULL on a purged trainer's relationships, and scrubs a purged trainee's trainer-set name and contact phone from kept free text.
- [ ] No log line, error body or Sentry event carries the name or phone.
- [ ] Contract, api-client method, route test and authz test exist for the endpoint; `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.
