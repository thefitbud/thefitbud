## Outcome
Signing in as a trainer on an iPhone dev build no longer red-boxes. Every core timezone helper accepts the zones iOS Hermes rejects (starting with `Asia/Kolkata`) and still shows the right date and time; a zone that is truly unusable produces an error that names the zone and says what was wrong, never a wrong date and never a generic catch. The trainer screens use the trainer's own `timezone` from `/me`, not a hardcoded constant. **P0, first in line in W3b.**

## Context
- **Evidence (3 Nov 2026, Firoz's iPhone, iOS dev build of staging):** after tapping sign in on a trainer account, red box `Render Error: Incorrect timeZone information provided`. Component stack `<AttentionTab>`. Call stack: `getZonedParts` (`packages/core/src/timezone.ts`) ← `formatLocalDate` ← `localDateInTimezone` (`apps/mobile/src/lib/dates.ts`) ← `AttentionTab` (`AttentionTab.tsx:217`), reached via `runRestore` in `apps/mobile/src/auth/AuthProvider.tsx`. Android (ICU-backed) is not affected so far.
- **Root cause, confirmed upstream (not yet reproduced by us on the exact build):**
  - Hermes on Apple platforms has no tz data of its own; `PlatformIntlApple` validates `timeZone` against `NSTimeZone.knownTimeZoneNames`, which is incomplete. `Asia/Kolkata` is not in it (Apple lists the legacy `Asia/Calcutta`), so `new Intl.DateTimeFormat(..., { timeZone: "Asia/Kolkata" })` throws `RangeError: Incorrect timeZone information provided`. Sources: https://github.com/facebook/hermes/issues/1100 (Asia/Kolkata on iOS, maintainer confirms `Asia/Calcutta` works), https://github.com/facebook/hermes/issues/1607 (root cause: `knownTimeZoneNames`), https://github.com/facebook/hermes/pull/1611 (fix: try `[[NSTimeZone alloc] initWithName:]` before throwing; its test plan lists `Asia/Kolkata`, `Etc/UTC`, `Etc/GMT`, `US/*` among previously failing zones), https://github.com/date-fns/tz/issues/32 (same error and `Asia/Calcutta` workaround).
  - **Suspected, not verified:** that the Hermes shipped with RN 0.76.9 / Expo SDK 52 does **not** contain #1611 (merged March 2025, commit `b8ad3c1`, after the 0.76 branch cut). The implementer confirms by running the probe below on the device, not by reading release notes.
  - **Ruled out as the trigger:** `hourCycle: "h23"` and case handling. The message is the timeZone-validation branch; the reports above reproduce it with only `{ timeZone }`. Keep `hourCycle` unless the device probe says otherwise.
- **Data exists for (b):** `users.timezone` (`apps/api/src/db/schema.ts:21`, `text NOT NULL DEFAULT 'UTC'`) is returned for every user, trainer included, in the identity/me payload (`apps/api/src/auth/identity.ts:209`, `packages/contracts/src/identity.ts:49` `timezone: z.string().min(1)`). Trainee screens already read `me?.timezone`. No migration, no API change. Note the default `UTC` is a valid value, so a trainer who never set a zone sees UTC; whether to prefer the device zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`) in that case is **D-W3b-11** below.
- **Same path on the trainee side:** `TodayTab.tsx:151` → `localDateInTimezone(timeZone)` → `getZonedParts`. A trainee whose profile says `Asia/Kolkata` (the seed and QA default) will crash the same way on iOS once they reach Today.
- Firoz's rule (D-W3-12, D-W3-18): every error says what actually went wrong; no generic catch.

## Gap list
- `getZonedParts` and the other core Intl calls pass the stored IANA name straight to Hermes; iOS rejects valid names missing from `knownTimeZoneNames`.
- `AttentionTab.tsx:71`, `ClientsTab.tsx:228`, `CheckinReviewScreen.tsx:151` hardcode the trainer's zone.
- `greeting.ts:23` swallows a zone error and shows IST.
- Written against `main` at f7d822e. The implementer re-checks each item against the latest `main` before building (AGENTS.md).

## Approach (suggested; implementer may choose another that meets the criteria)
1. One core helper, e.g. `resolveIntlTimeZone(zone)`, used by every core Intl call that takes a zone. It tries the zone as given; if the engine throws `RangeError`, it tries a **small, explicit, tested alias table** of canonical ⇄ legacy names that denote the same zone (at least `Asia/Kolkata`⇄`Asia/Calcutta`, `Etc/UTC`/`UTC`, plus the other names in #1611's list that map 1:1, e.g. `Asia/Ho_Chi_Minh`⇄`Asia/Saigon`, `Asia/Kathmandu`⇄`Asia/Katmandu`, `Europe/Kyiv`⇄`Europe/Kiev`). Result is cached per input.
2. Aliases only. **Never** fall back to UTC, IST, the device zone, or a fixed offset to "make it work" — that would show a wrong date silently.
3. If nothing works, throw a typed error (e.g. `UnsupportedTimeZoneError`) whose message names the zone and the engine's own reason, e.g. `Time zone "Foo/Bar" is not supported on this device (tried: Foo/Bar). Engine said: Incorrect timeZone information provided`. Callers do not catch it generically; the screen's existing error boundary/banner shows it.
4. `AttentionTab`, `ClientsTab`, `CheckinReviewScreen` read the trainer's zone from the **device** (`Intl.DateTimeFormat().resolvedOptions().timeZone`), per **D-W3b-11 as decided (option (b), Firoz, 4 Nov 2026)**, falling back to `Asia/Kolkata` when it cannot be read and never to UTC. Delete `TRAINER_ZONE`. **Corrected 4 Nov 2026:** this line previously said `me.timezone`, which was the option-(a) default the decision carried while it was Open.
5. Remove `greeting.ts`'s silent IST catch; it uses the resolver like the rest.

## Decisions needed
- **D-W3b-12 Widen CU17 to the mobile direct Intl calls, with a bypass guard. Decided by FitBud UI, 3 Nov 2026.** `CheckinScreen.tsx:937`, `ReminderSetupScreen.tsx:46`, `ForegroundBanner.tsx:18`, `NotificationsScreen.tsx:130`, `MoreScreen.tsx:91` and `AttentionTab.tsx:612` pass a zone to `Intl` themselves and would still crash on iPhone for an `Asia/Kolkata` user, so they are in CU17 and go through the same core resolver. CU17 also adds a guard (lint rule or test) so no new `timeZone:` Intl call bypasses the resolver. The ~20 trainee `?? "Asia/Kolkata"` fallbacks stay a follow-up: the resolver makes them safe.
- **D-W3b-11 DECIDED (option (b), Firoz, 4 Nov 2026):** trainer screens use the **device** timezone; if it cannot be read, fall back to `Asia/Kolkata`; **never UTC**; a zone that is present but unresolvable still throws an error naming it. The fallback is an explicit rule and reads as one in the code. **This line previously recorded the decision as Open and recommended stored-value-wins** — that recommendation was not taken. See also D-W3b-11a for the device probe that preceded the decision, and D-W3b-20 for what the single build from `main` must still check.
