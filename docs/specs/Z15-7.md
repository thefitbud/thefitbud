## Outcome
A repeated finish, a skip after a finish, or a lock-screen set that arrives after the finish never creates a second record or a scary error: the server answers each one idempotently and applies each workout step atomically.

## Context
- Diagnosis #13. Z15-8 is the app side. One execution per assignment is already enforced (`drizzle/0004_workouts.sql:43`).
- AGENTS.md API rules: idempotency keys for retryable mutations, optimistic concurrency, conflicts returned never silently overwritten, static error messages.

## Gap list
- `POST /workouts/executions/:id/complete` on an already-completed execution fails (`workouts.ts` near `:1497-1530`); a second complete with a new key is not recognised as the same action.
- `POST /workouts/assignments/:id/skip` on a finished workout: "Workout already finished and cannot be skipped." (`:1759`).
- `.../sets/:setId/complete` on a finished workout: "Sets can only be completed during an open workout." (`:1297`).
- Multi-statement writes (complete + set rows + exceptions + change log) run as separate statements.
- Written against `main` at `2c9819d3`. Re-check each item on the latest `main` before building; drop what is done and say so in the PR (AGENTS.md).

## Acceptance criteria
- [ ] Complete on an execution that is already completed returns `200` with the stored execution and a flag (`alreadyCompleted: true`, additive), not an error, when the body is compatible (same or no RPE); a different RPE is a conflict (`409 WORKOUT_ALREADY_FINISHED`, static message) unless Z15-11's endpoint is used.
- [ ] Skip on a completed workout returns a stable code `WORKOUT_ALREADY_FINISHED` (409) that the sync layer reports as `already_applied`-equivalent (the trainee's intent is moot), never a refusal the trainee must act on.
- [ ] A set complete for a finished execution: if the set is already logged with the same values → `200` no-op; otherwise `409 WORKOUT_ALREADY_FINISHED` with no write; sync maps it to a resolved verdict with a note for the sync status screen ("This set arrived after you finished the workout, so it wasn't added."). No silent edit of a finished workout (published records stay intact).
- [ ] Each workout write that touches several tables runs in one `db.batch` (atomic); a forced failure mid-write leaves nothing half-applied (test).
- [ ] `packages/api-client` maps `WORKOUT_ALREADY_FINISHED` to friendly copy (D-W15-3).
- [ ] Sync and workout tests pass; `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.

## Out of scope
- Product rules (AGENTS.md, never break): only the trainer resolves an exception; no auto-send (WhatsApp is a wa.me prefill the user sends); no percentages or streaks; dates read like "Wed 21 Oct", never ISO or raw enums; payments are tracking only; ended clients are read-only on server and UI.
- Error copy (D-W15-3): friendly copy only, never raw error codes, HTTP statuses, `err.message` or bracketed codes on screen; say what actually went wrong; keep a way forward. Map through `userFacingMessage`/`userFacingError`.
- Working rules: no remote or deploy commands; no secrets; one branch `claude/<ID>-<slug>`, one PR `<ID>: <summary>` off the latest `main`, updated by merging `main` (never rebase or force-push); never cancel an Actions run; never write the mention handle.

## Tests to add

- Atomicity: injected failure in the batch leaves no partial rows.
