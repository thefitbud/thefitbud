## Outcome
A trainer can log a finished workout for a client or edit any set of a client's workout entry; each change is audited, appears in the trainer activity feed, and pushes the client when their setting is on.

## Context
- Trainer log and edit, in the beta per Firoz 4 Nov 2026 (PLAN-v2 **D-P2-21**, replacing the live-logging part of D-P2-15). Live logging by the trainer (one client or several in parallel) is **on hold, Phase 10 (W14 Z14-5, Z14-14, Z14-15)**. Rules (recommended defaults, Firoz can override): **R1** an entry the coach created is read-only to the trainee, labelled "Logged by your coach"; an entry the trainee logged and the coach edited stays the trainee's, labelled "Edited by your coach". **R2** trainers skip the Z6-11 log-time limits, but an entry's date must be within the last 7 days and not in the future; edits are allowed on entries dated within the last 7 days. **R3** a coach-created or coach-edited entry counts once toward adherence, keyed by the entry id, never double-counted. **R4** every trainer create or edit writes one audit record (who, what, when, before and after) and one activity-feed event. **R5** the trainee gets a push for each trainer create or edit only if their "Coach updates to my logs" setting is on (default on; respects push on/off and quiet hours; merged per entry within 10 minutes). Ended clients are read-only (no create or edit).
- In scope (client-side logs that exist on `main` at c677957): **workouts** (`workout_executions` + `set_executions`), **meals** (`meal_compliance`: followed, deviated or skipped, with the deviation note), **body measurements** (`measurements`, incl. weight). **Not in scope:** check-ins (the client's own answers that the trainer reviews; editing them would change what the review is about), steps (no steps log on `main`; Z9-9 reads device totals, which are not editable), progress photos.
- Written against `main` at c677957. The implementer re-checks each item against the latest `main` before building (AGENTS.md).
- New `POST /workouts/assignments/:id/log` (trainer, idempotency key): whole workout in one body (exercises, sets with reps and `load_kg` or Bodyweight, optional session RPE, `performedAt`); creates a completed execution with `logged_by_role=coach`.
- New `PATCH /workouts/executions/:id` (trainer): edit sets (reps, kg, done/skipped) and `performedAt` on a completed execution of an active client within R2's 7 days; sets `last_edited_*`.
- Shared domain `coach-log.ts` (used by Z6-20): `recordCoachLogChange({entity, action, before, after})` writes `log_edit_events`, a change-log upsert, and enqueues a `coach_log_updated` notification through `inbox-notify.ts` when `coach_log_updates` and push are on (quiet hours respected, `merge_group` = entity id, 10-minute merge).
- `activity-feed.ts`: emit `coach_logged` / `coach_edited` events from `log_edit_events` (actor name, entity, date, a short before → after summary).
- R1: trainee writes to a coach-created execution return `409 coach_logged_read_only`; trainee reads include `loggedByRole`, `lastEditedByRole`. R3: adherence reads executions by id, so an edit never adds a second count.

## Acceptance criteria
- [ ] Trainer form log creates one completed coach execution; backdate over 7 days or in the future returns `422 backdate_limit`.
- [ ] Trainer edit changes the sets, writes one `log_edit_events` row with before and after, and sets `last_edited_*`.
- [ ] Activity feed lists the create and the edit with actor and summary.
- [ ] Push is enqueued only when `coach_log_updates` is on; two edits within 10 minutes merge into one.
- [ ] Another trainer's client or an ended client returns `403`/`409`; trainee writes on a coach-created execution return `409`.
- [ ] Adherence counts the workout once after a retried log and after an edit.

## Out of scope
- Live logging by the trainer during a session, one client or several in parallel (on hold, Phase 10: W14 Z14-5, Z14-14, Z14-15; DS8 b/c frames approved and parked). Sessions, attendance, roll call, calendar, agenda, reminders (W14).
- Product rules (CLAUDE.md, never break): only the trainer resolves an exception (no auto-resolve); no auto-send (WhatsApp is a wa.me prefill); no percentages or streaks; payments are tracking only; ended clients are read-only on server and UI.
- Working rules (CLAUDE.md): never run remote or deploy commands; no secrets in code, logs or commits (only `.example` env files and the demo seed); one task, one branch `claude/<ID>-<slug>`, one PR `<ID>: <summary>` off the latest `main`; update by merging `main`, never rebase or force-push.
