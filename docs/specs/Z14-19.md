## Outcome
Wherever a client's picture and name appear in a trainer list or detail header, tapping them opens that client's profile, and Back returns to where the trainer was.

## Context
- Diagnosis #16. **D-W14-27** (avatar/name is the profile link; where it is not). D-W14-24 (back).
- Six screens, each a one-line wiring change on the shared `ClientAvatar`; the Attention rows (Z14-22) and the review sheet header (Z14-23) adopt `ClientAvatar` in their own tasks.
- `TrainerShell.openClientById` (`:125-157`) scans `listClients({ limit: 50 })` for the name; clients past 50 open as "Client" / "Unknown".

## Acceptance criteria
- [ ] `ClientAvatar` (initials and tone exactly as today's per-screen avatars, sizes 40 and 56/64), pressable together with the name next to it, minimum 44×44 pt target, `accessibilityRole="button"`, label "Open {name}'s profile", pressed state per the kit; renders as plain (not pressable) when no `onPress` is given.
- [ ] Used in: Activity feed rows (avatar opens the profile; the rest of the row still opens the event), Check-ins list rows, Check-in review header, Ask detail header, Session detail header, Exception screen header.
- [ ] Not a link inside the client's own pages (client page header, diet day, client log, goal and intake) or in pickers (`activity/ClientPickerSheet.tsx`).
- [ ] The profile opens pushed on top of the current screen (`open`, not `startAt`), so Back (on-screen or Android) returns to the screen the trainer tapped from, scroll kept.
- [ ] The shell gets the name and status from the client-meta cache (Z14-3) or the client workspace header, not from a 50-row page; a client past the first 50 opens with the right name.
- [ ] Offline: tapping still opens the cached profile (Z14-3 snapshot) or its offline state; no dead tap.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.

## Out of scope
- Product rules (AGENTS.md, never break): only the trainer resolves an exception; no auto-send (WhatsApp is a wa.me prefill the user sends); no percentages or streaks; dates read like "Wed 21 Oct", never ISO or raw enums; payments are tracking only; ended clients are read-only on server and UI.
- Error copy (D-W14-3): friendly copy only, never raw error codes, HTTP statuses, `err.message` or bracketed codes on screen; say what actually went wrong; keep a way forward. Map through `userFacingMessage`/`userFacingError`.
- Working rules: no remote or deploy commands; no secrets; one branch `claude/<ID>-<slug>`, one PR `<ID>: <summary>` off the latest `main`, updated by merging `main` (never rebase or force-push); never cancel an Actions run; never write the mention handle.
