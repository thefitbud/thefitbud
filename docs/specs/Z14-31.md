## Outcome
A trainee can save a short note with their session rating on a finished workout, change it for 48 hours, and the trainer's reads, activity feed and sync pull carry it. This is the one new column that D-W14-18 forbade in the first pass; Firoz allowed it on 25 Nov 2026 (**D-W14-34**).

## Context
- Z14-11/Z14-12 built RPE only: `workout_executions` has no note column, the feedback endpoint is `.strict()` and refuses `note` (`packages/contracts/src/workout.ts:204-219`), and the route text says "A note is not stored" (`apps/api/src/routes/workouts.ts`, `PATCH /executions/:executionId/feedback`, about `:2700-2860`). D-W14-10 and **D-W14-20** (rating and note editable for 48 h) and mock frames W-17a2/W-17c/W-17c2 (`docs/design/mockups/z14-10/`) already specify the behaviour; only storage and transport are missing.
- Mobile (Z14-32, after this task) adds the field to the summary and a "Note from {First}" card to the trainer's session screen. Trainer web has no workout-session screen today (only plan and progress views read RPE), so web is out of scope.
- The note travels **only through the feedback endpoint and its sync mutation** (`workout.feedback`, `apps/api/src/routes/sync.ts:72,213`). `POST …/complete` is unchanged: the summary where the note is typed comes after the finish.
- Existing 48 h window: `feedbackEditableUntil` (`domain/meal-edit-window.ts`, `workoutFeedbackEditableUntil`); offline changes inside the window are accepted if they arrive within 72 h of it closing. Keep both rules exactly.

## Acceptance criteria
- [ ] Migration `0043_*` (next free number; renumber at merge if another lands) is **additive and nullable**: `ALTER TABLE workout_executions ADD COLUMN session_note text;`, no default, no index, no backfill, no other statement. `schema.ts` matches; the migration-chain test passes; `PRAGMA optimize` still runs after migrate (Z14-4 scripts, unchanged).
- [ ] Contract: `traineeWorkoutFeedbackRequestSchema` becomes `{ rpe?: int 1..10 | null, note?: string | null, recordVersion }`, still `.strict()` (unknown keys refused), **at least one of `rpe` and `note` present** (otherwise a 400 with friendly copy). An omitted key means "unchanged"; `note: null`, `""` and whitespace-only clear the note. A note is trimmed and at most **500** characters (over-length is refused, never cut). The old `{ rpe, recordVersion }` body from Z14-12 clients still validates and behaves as today.
- [ ] `workoutExecutionSchema` gains `sessionNote: string | null` (optional in the schema so older fixtures parse, like `loggedByRole`); the API always sends it on REST reads, trainer reads and sync pull payloads.
- [ ] `PATCH /workouts/executions/:executionId/feedback` stores the note with the RPE in **one atomic write** (`db.batch`, as the rating write does today), inside the same 48 h window (`422 FEEDBACK_EDIT_WINDOW_CLOSED` after it), same version rule (`409 VERSION_CONFLICT` on a stale `recordVersion`), same ownership rules (the trainee's own finished workout only; a coach-logged entry stays read-only; an ended relationship is read-only). A request whose values equal the stored ones answers 200 with the stored execution and **no version bump, no change-log row, no activity item** (as today for an equal RPE).
- [ ] `SESSION_RPE_REQUIRED` fires only when `rpe: null` is sent explicitly and the plan requires a rating. A note-only request never triggers it, and never clears a stored rating.
- [ ] Change log: the stored before/after snapshot includes the note; the description lines read `Note: added`, `Note: changed` or `Note: removed` and never contain the note text. The activity item for the trainer reads "Rated {workout}: RPE n" for a rating, "Rated {workout}: RPE n · left a note" when both changed, "Added a note on {workout}" / "Changed the note on {workout}" / "Removed the note on {workout}" for a note-only change. The note text is never in the feed summary.
- [ ] No push and no inbox notification for a note or rating change (D-W14-34 c): the trainer sees it in Activity and on the session screen. A realtime hint is sent as today.
- [ ] Sync: a `workout.feedback` mutation with a note applies through the same path as REST (same 72 h late rule, idempotent replay by mutation id, a refused row carries a friendly reason). No new mutation type; `apps/api/src/domain/sync.ts` returns the note on pull.
- [ ] OpenAPI text for the route and the execution schema no longer says "A note is not stored".
- [ ] Hot-read query counts do not rise (`hot-reads.query-count.test.ts`, `cold-start.query-count.test.ts` still pass unchanged).

## Decide-and-note
1. **Length 500 (recommended):** matches a short sentence or two, same order as the meal note; refuse rather than truncate.
2. **Rating omitted vs null (recommended):** omitted = unchanged, `null` = clear, as above, so a note edit can never wipe the rating.
3. **No notification (recommended):** Activity item only, like the RPE change today.
4. **Feed wording:** the words above; adjust only to keep the existing rating wording stable for old rows.
