## Outcome
Meal photos that are still waiting to upload behave correctly around two events: **sign-out** (the queue and its stored files are removed, and nothing uploads while signed out or as someone else) and **edits** (a photo never attaches ahead of a pending edit or removal of the same meal, and the next edit after an attach uses the version the attach produced, so it is not refused).

## Context
- Z14-13 fix round 1 made meal photos durable jobs (`apps/mobile/src/trainee/food/mealPhotoJobs.ts`, kept in the device store under `fitbud.mealPhotoJobs.v1`, one runner per signed-in user for the process via `mealPhotoJobsFor`). The W14 Report lists three follow-ups: sign-out does not clear queued photos; the runner should wait for pending `meal.edit`/`meal.remove` rows; the stored server version should be updated after an attach (Z14-13b).
- Sign-out today: `AuthProvider.tsx` `endSession(unsentLogs)` (`:860-908`) clears unsent logs with `clearSyncDataOnSignOut()` (`sync/userStore.ts:91`) when the user explicitly signs out ("drop"); a session the server ended keeps them keyed by user id (Z12-41). Photo jobs are not part of that.
- The attach endpoint, its idempotency keys and the 24 h meal edit window are Z14-11/Z14-13 (`POST …/photo`, `PATCH …` entry edit, `recordVersion` rules). Do not change the API.
- Privacy: a photo of a meal is the trainee's data; after "Sign out" the sheet says unsent logs are dropped (TR-20f), so queued photos must go too.

## Gap list
Written against `main` at `1a6bdc04`. Re-check each item on the latest `main` before building; drop what is done and say so in the PR (AGENTS.md).
- `endSession("drop")` does not dispose the photo runner or delete its job records and stored bytes; the singleton keeps timers and subscriptions alive for the old owner.
- `createMealPhotoJobs` decides readiness from "the log has a server entry id and is not in the outbox" (`serverEntryId`, `pendingMealLogIdsAll`); it does not look at a pending `meal.edit` or `meal.remove` for that entry. An attach ahead of a queued edit races it; an attach to a meal removed meanwhile fails or attaches to nothing.
- After a successful attach the entry's `recordVersion` has moved on, but the device keeps the old one, so the next edit sends a stale version and the server answers a version conflict.

## Acceptance criteria
- [ ] Explicit sign-out (`endSession("drop")`): the user's runner is disposed (timers, reachability and outbox subscriptions stopped), every job record, the index and every stored byte for that owner are deleted, and a late completion from an in-flight upload does not recreate anything. No upload or attach happens after the session is cleared.
- [ ] A server-ended session (`endSession("keep")`): the runner stops, the jobs stay in the store keyed by owner, and the **same** user gets them back on the next sign-in; a different user on the phone never sees, sends or deletes them (owner check on the index, as today).
- [ ] The runner attaches only when the meal's entry has **no pending outbox row** of `meal.log`, `meal.edit` or `meal.remove` for it. It re-checks when the outbox changes (the same trigger it uses for `meal.log`), not on a blind timer.
- [ ] If the entry was removed (a settled `meal.remove`, or the server says the entry is gone), the job is dropped and its bytes deleted, with no error shown (the log no longer exists). A removal still pending keeps the job waiting.
- [ ] After a successful attach, the entry's stored server version is updated from the attach response so the next `meal.edit` in the same session, and after a restart, sends the post-attach version. A test shows the old behaviour would send the stale version.
- [ ] Failure copy and states are unchanged (`FAILED_COPY`, offline neutral).
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.

## Decide-and-note
1. **Keep vs drop on a removed entry (recommended):** drop silently; the meal and its photo are gone by the trainee's own action.
2. **Where the version lives (recommended):** whichever store the Diet snapshot/outbox already uses for an entry's `recordVersion`; do not add a new store. Record which in the PR.
3. **Clearing order on sign-out (recommended):** dispose the runner first, then delete records, then bytes, so nothing can write in between.

## Tests to add
- Sign-out drops jobs and bytes and stops a running upload from recreating them (mutation-check: remove the dispose call and it must fail). Session-ended keeps them and another owner cannot read them.
- Waiting behind a pending `meal.edit` and a pending `meal.remove`; resumes when the outbox drains; removal drops the job.
- Version after attach is used by the next edit.
