## Outcome
Every trainer and trainee screen's API call answers in a small, fixed number of D1 round trips, so Needs you, Clients, a client's page, Today, Diet, Workout and Progress feel instant from India.

## Context
- Diagnosis #1 (`docs/specs/batches/W14-diagnosis.md`), FitBud Tech's measurement (summarised there): ~123 serial queries for Needs you with 21 clients (33 s from the US, est. 6–10 s from India), 7–14 serial trips on most screens, 5 auth queries per request. Queries are fast (8–25 ms per screen locally); the cost is round trips.
- D-W14-8 (Needs you reads stored exceptions; ≤ 12 queries for 21 clients). D-W14-6 is the client side (Z14-2, Z14-3).
- D1 supports `db.batch([...])` (one round trip, one implicit transaction); use it for independent reads and for read-then-write groups that must be atomic. `Promise.all` over separate statements still costs one trip each on D1; prefer `batch`.
- Existing query-count tests cap some paths (`apps/api/src/routes/exceptions.query-count.test.ts`); extend that pattern.

## Gap list
- `domain/exceptions.ts:453-454` evaluates every relationship on each `GET /exceptions/attention` read (`routes/exceptions.ts:222`).
- `auth/identity.ts:253-260`, `:172`, `:183`, `:188`, `:193`: 5 serial queries to resolve the actor; `middleware/auth.ts:134-137` writes `last_seen_at` on every web request.
- `routes/sync.ts:267`, `:314`: each mutation is re-dispatched as an HTTP sub-request that re-runs auth (Firebase verify + 5 queries).
- Hot read routes run their queries one after another (Today `GET /me/day`, meal and workout assignment lists, progress summary, check-ins list, clients list, workspace/client page, coach asks, notifications inbox).
- No `Cache-Control`/`ETag` on JSON reads except `/config`.
- Written against `main` at `2c9819d3`. Re-check each item on the latest `main` before building; drop what is done and say so in the PR (AGENTS.md).

## Acceptance criteria
- [ ] Needs you: evaluation moved to the write paths that change exceptions and the existing cron; the read path reads stored rows and re-evaluates only relationships last evaluated > 15 min ago, in one batched pass. A query-count test with the demo trainer's 21 clients asserts ≤ 12 queries, and the same count with 5 and 40 clients (flat). Exception results for the demo seed are identical before and after (snapshot test). No auto-resolve.
- [ ] Clients list (`GET /clients`) answers without evaluating exceptions; trainer mobile's Clients tab no longer needs the attention call for its badges (expose the counts it needs on the clients list, additive contract field, or document why not).
- [ ] Actor resolution is one query (a join or one `batch`), cached per request; `last_seen_at` is written at most once per 5 minutes per session. Auth tests (authorization matrix, archived users, role selection, dual role) pass unchanged.
- [ ] `sync/push` applies mutations in-process without re-running auth per mutation (resolve the actor once, call the handlers' domain functions or an internal dispatcher that reuses the context); idempotency, dedupe and per-mutation verdicts unchanged (`sync*.test.ts` pass).
- [ ] Each hot read path listed in the gap list issues its independent reads in one `db.batch` (or a single query) and has a query-count test with a cap written in the test; the PR has a before/after table of query counts per endpoint for the demo trainer and the demo trainee (`aarav.ontrack`).
- [ ] Read endpoints for the trainee day and week return a weak `ETag` and honour `If-None-Match` with `304` where the response is a pure function of stored state (optional if the api-client cannot pass it without contract churn; record the choice).
- [ ] No contract break: `packages/contracts` changes are additive only; trainer web e2e and mobile tests pass.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test`, trainer-web e2e pass.

## Out of scope
- Product rules (AGENTS.md, never break): only the trainer resolves an exception; no auto-send (WhatsApp is a wa.me prefill the user sends); no percentages or streaks; dates read like "Wed 21 Oct", never ISO or raw enums; payments are tracking only; ended clients are read-only on server and UI.
- Error copy (D-W14-3): friendly copy only, never raw error codes, HTTP statuses, `err.message` or bracketed codes on screen; say what actually went wrong; keep a way forward. Map through `userFacingMessage`/`userFacingError`.
- Working rules: no remote or deploy commands; no secrets; one branch `claude/<ID>-<slug>`, one PR `<ID>: <summary>` off the latest `main`, updated by merging `main` (never rebase or force-push); never cancel an Actions run; never write the mention handle.
