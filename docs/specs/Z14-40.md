## Outcome
After a signed-in cold start on a phone that already has this user's `/me` and relationships snapshot, the first screen appears without waiting for `listRelationships` (about 0.2–0.4 s from India). The live call still runs and replaces the snapshot when it answers. A refused session still signs the person out.

## Context
- FitBud Tech's 25 Nov 2026 audit: startup still waits on the relationships call even after Z14-28 cut the server work on that route, and after Z14-3 stopped waiting on push registration.
- On `main` at `ddd48f22`, `AuthProvider.applyMe` still `await`s `loadRelationships` before `runRestore` sets `bootstrapping` to false. `resolveAppRoute` treats `relationships === null` as `"loading"` for a trainee. The snapshot is used today when the device is offline, or when `/me` succeeded and the relationships call then failed — not on a normal online start.
- Trainer routing does not need relationships to open the trainer shell, but `applyMe` still waits for the call for both roles before the restore finishes, so trainers wait too.
- **D-W14-39**, **D-W14-41**. No new storage dependency; use the existing `meSnapshot` store. No API or contract change. No migration.

## Gap list
Written against `main` at `ddd48f22`. Re-check each item on the latest `main` before building; drop what is done and say so in the PR (AGENTS.md).
- Online restore: `await applyMe` blocks the first screen on `listRelationships` even when a snapshot for this user is already on the phone.
- A successful live relationships (and `/me`) answer must still replace the snapshot and leave snapshot mode, as today.

## Acceptance criteria
- [ ] When a stored snapshot for this user exists, the first screen is chosen from that snapshot as soon as `/me` (or the already-restored session) has succeeded, without waiting for `listRelationships`. The live relationships call continues in the background and, when it answers, updates the in-memory list, persists the snapshot, and leaves snapshot/offline mode if it was only used for this paint.
- [ ] If there is no snapshot, behaviour stays as today: wait for the live call (or show the existing offline / retry path if the call fails).
- [ ] A 401 or a refused session still signs the person out and does not open the shell from a snapshot (existing `dropRefusedSession` / refused restore paths stay).
- [ ] Role select, intake, waiting-for-review, ended coaching and trainer shell are still chosen by the same `resolveAppRoute` rules, first from the snapshot and then from the live list if it differs (for example a newly ended relationship). There must be no flash of the wrong shell when the live list arrives; if the route would change, move once, with no raw error.
- [ ] Push registration stays off the critical path (Z14-3). This task must not start awaiting it again.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.

## Out of scope
- Product rules (AGENTS.md, never break): only the trainer resolves an exception; no auto-send (WhatsApp is a wa.me prefill the user sends); no percentages or streaks; dates read like "Wed 21 Oct", never ISO or raw enums; payments are tracking only; ended clients are read-only on server and UI.
- Error copy (D-W14-3): friendly copy only, never raw error codes, HTTP statuses, `err.message` or bracketed codes on screen; say what actually went wrong; keep a way forward. Map through `userFacingMessage`/`userFacingError`.
- Working rules: no remote or deploy commands; no secrets; one branch `claude/<ID>-<slug>`, one PR `<ID>: <summary>` off the latest `main`, updated by merging `main` (never rebase or force-push); never cancel an Actions run; never write the mention handle.
- API or contract changes, migrations, trainee day-cache work (Z14-44), More tab (Z14-39), held feedback (Z14-41).

## Decide-and-note
1. **When to paint from the snapshot (recommended):** as soon as restore has a valid session and a snapshot for this user, even if `/me` has also just answered, rather than waiting for relationships. If `/me` has not answered and the snapshot is only usable on the existing offline path, keep that path; do not invent a third mode.
2. **Trainer (recommended):** the same rule — do not block `bootstrapping` on `listRelationships` when a snapshot (or a trainer route that does not need it) is ready.

## Tests to add
- Online cold start with a stored snapshot: the trainee (and trainer) shell is reachable before `listRelationships` resolves; when it resolves, the live list replaces the snapshot. Mutation-check: if `applyMe` still awaits the call before leaving the loading route, the test must fail.
- No snapshot: the first screen still waits for the live call.
- 401 / refused session: the snapshot is not shown.
- Keep the existing offline and "relationships fail after `/me`" tests green.
