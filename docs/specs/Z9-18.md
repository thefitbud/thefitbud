## Outcome
When a trainer sets a client's display name or contact phone in Client settings, Home, the Clients list, the client workspace header and every WhatsApp draft built from those payloads use them.

## Context
- Added 11 Nov 2026 from the W8 report follow-ups (frame 210 helper question; D-W9-8). FitBud UI brief approved by Firoz.
- **D-W8-10** (planner, 7 Nov 2026): Client settings write only the relationship display name (`coaching_relationships.client_display_name`, exposed as `relationship.clientDisplayName`) and contact phone (`contact_phone_e164`, `contactPhoneE164`), added by Z6-8b / Z7-25. **Never write `user_identities.mobile_e164` or `trainee_profiles.display_name`.** This task only reads.
- **Name rule** (`traineeDisplayName`): `relationship.clientDisplayName` if set (non-empty), else the trainee profile `displayName`, else the existing invitation fallbacks each builder already uses (unchanged).
- **Phone rule** (`clientWhatsappE164` and any other WhatsApp draft source): `relationship.contactPhoneE164` if set, else the sign-in `user_identities.mobile_e164` (today's behaviour).
- Put both rules in one small resolver, `apps/api/src/domain/client-identity.ts` (pure functions over already-loaded rows, no provider code), and call it from:
  - `apps/api/src/domain/directory.ts` (Clients list; also used for its search, which must match the trainer-set name),
  - `apps/api/src/domain/workspace.ts` (~l.738–779: header `traineeDisplayName` and `clientWhatsappE164`, which feed the header WhatsApp button and the Reminders drawer wa.me drafts),
  - `apps/api/src/routes/exceptions.ts` (~l.237–282, ~l.332: Home queue groups and the review panel's name and WhatsApp number). Its rows come from `listAttentionExceptionsForTrainer` in `apps/api/src/domain/exceptions.ts` (~l.428), which already joins the relationship but returns only `coachingRelationshipId` and `traineeUserId`; return `clientDisplayName` and `contactPhoneE164` from that same select. `exceptions.query-count.test.ts` must keep its statement count and snapshot.
  - `apps/api/src/domain/responsiveness.ts` `deriveReengagementCandidates` (~l.458–530): Home's **"Re-engage on WhatsApp"** section (`/notifications/reengagement-candidates`) builds the name, phone and `waMeUrl` draft from `trainee_profiles` and `user_identities.mobile_e164` only.
  - `apps/api/src/routes/activity-feed.ts`: Home's **"Recent activity"** shows `traineeDisplayName` from this route.
  Each needs the relationship columns in its existing select; add them to the select, do not add round trips.
- The check-in review list name in `checkins.ts` is **not** in this task (not Home, Clients or a WhatsApp draft); list it and anything else you find in the PR as follow-ups. Home, Clients and the workspace/review-panel WhatsApp drafts are what Z9-19's helper text promises, and they must all be wired here.
- **Serial after Z9-15** (same lane; both own `directory.ts` and `packages/contracts/src/directory.ts`). Merge `main` after Z9-15 lands before starting.
- Ownership: every lookup stays scoped to the acting trainer's relationships; the resolver never takes ids from the request.
- No migration; the columns exist (Z6-8b).
- Re-check each gap item against the latest `main` before building (AGENTS.md).
