## Outcome
A trainee can submit a check-in that answers only what the pinned form asks: `wellbeing` is required only when the pinned form marks it required (v1 does, v2 does not), and every measurement answer is stored, so a v2 check-in with both arm and thigh keeps both, in cm.

## Context
- Product direction: Firoz, 7 Nov 2026 (D-W6-42). Background: D-W6-17 (v2 field shape), D-W6-18 (why the default could not flip), D-W6-19 (Z6-2 parked), D-W6-41 (order Z6-6 → Z6-2b → Z6-2c → Z6-2 → Z6-7, and amendment (5): Z6-6 owns the submit hook in `checkins.ts` first).
- **Builds on Z6-6 (#286).** Z6-6 adds `key` to the field schema, `invalidCheckinKeyedAnswers` on the submit path in `checkins.ts`, and the core `checkin-keys.ts` exports. Z6-2b starts after Z6-6 merges, merges `main` first, and leaves Z6-6's code in place.
- **No default flip here.** New assignments keep defaulting to v1. Z6-2 flips the default after Z6-2c (D-W6-41 (4)). No migration in this task.
- **The `wellbeing` rule.** The submit route already checks required answers against the pinned form's fields (`missingRequiredCheckinAnswers(answers, pinned.fields)`), and v1's `wellbeing` field is `required: true`. What blocks a v2 submit is the contract: `checkinAnswersSchema.wellbeing` is required for every check-in, so a v2 submit without it fails with 400 before the form is read. Making it optional in the contract leaves v1 enforced through its form (422 `CHECKIN_ANSWERS_INCOMPLETE`). When `wellbeing` is sent, it must still be non-blank (keep `.trim().min(1)`). The no-fields fallback in `missingRequiredCheckinAnswers` (no pinned form) keeps requiring `wellbeing`.
- **Storage for arm and thigh (recommended default, D-W6-34; from the measurements schema).** `measurements.type` allows only `body_weight_kg`, `waist_cm`, `hip_cm`, `chest_cm` and `other`, and the table has no label or key column. So each answered `other` question becomes its own `measurements` row: `type = 'other'`, `unit` = the question's `unit` (`cm` for v2 arm and thigh), `source = 'checkin'`, `checkin_id` set. Which body part a row is lives in the check-in answer (`fieldAnswers.arm`, `fieldAnswers.thigh`), which is what Z6-7 charts by key. No new column, no migration. Known limitation, not fixed here: generic measurement lists show both rows as "other".
- **Linked measurements rule.** `linkedMeasurementsForCheckin` today skips a second question of the same measurement type and stores `other` with the unit "unit" (`defaultUnitForMeasurementType`). New rule: one row per answered measurement question (de-duplicated by question id, not by type), each returning its unit (the question's `unit` when set, otherwise the type's default). The legacy `bodyWeightKg` answer still adds a `body_weight_kg` row only when no question already produced one.
- **One shared answer list for the review screens (recommended default, D-W6-34).** Add a pure core helper, for example `checkinAnswerEntries(fields, answers)`, that returns the answered questions of the pinned form in form order (field id, key, label, type, unit, value), reading `fieldAnswers` first and the legacy `wellbeing`, `notes` and `bodyWeightKg` only for the v1 fields they belong to, and skipping unanswered questions. It never adds an entry the form does not have. Z6-2c uses it on mobile and web, so both apps show the same answers (AGENTS.md: shared rules live in core, not copied per app). Export it with one line in `packages/core/src/index.ts`.
- Stored answers are never rewritten, including any `"OK"` sent by the old mobile code (AGENTS.md: no rewriting historical coaching records).

## Acceptance criteria
- [ ] `submitCheckinRequestSchema` accepts answers without `wellbeing`; a blank `wellbeing` string, when sent, is still rejected.
- [ ] A check-in pinned to a form with v2's questions (all optional, no `wellbeing` question) submits without `wellbeing` and returns 200.
- [ ] A check-in pinned to global v1 submitted without `wellbeing` returns 422 `CHECKIN_ANSWERS_INCOMPLETE` with `missing: ["wellbeing"]` (static message, as today).
- [ ] A submit answering arm 32 and thigh 55 stores two `measurements` rows, both `type 'other'`, `unit 'cm'`, `source 'checkin'`, linked by `checkin_id`, with values 32 and 55.
- [ ] Weight answered through a question and through legacy `bodyWeightKg` stores one `body_weight_kg` row, not two.
- [ ] An idempotent replay of the same submit stores no extra measurement rows.
- [ ] The core answer-list helper returns only answered questions of the pinned form, in form order, with units; v1 `wellbeing` appears only for a form that has that question.
- [ ] Z6-6's key validation still runs on submit and its tests pass.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.
