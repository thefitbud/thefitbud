## Outcome
The app can record how hard a workout felt and change the note for 48 h after it is finished, attach a real photo to a meal that is already logged, and let the trainee edit or remove their own meal entry for 24 h after logging, with every action safe to retry, working offline through sync, and visible to the coach.

## Context
- Diagnosis #4 and #12. D-W14-10 and D-W14-20 (RPE and note editable by the trainee for 48 h after finish, read-only after), D-W14-11 and D-W14-19 (attach endpoint; the photo is only prompted when the assignment has `photoRequired`), **D-W14-22** (24 h meal edit/remove: window, what can change, remove rule, locks, coach visibility, offline rule) and D-W14-23 (what the coach is shown).
- The coach meal-entry route (`meals.ts` near `:1217`, "Trainer logs or corrects a client's meal entry") already replaces outcome, deviation and note with `recordVersion`, sets `last_edited_*`, audits and writes the activity feed: reuse its validation, versioning and audit path for the trainee edit, with the trainee's authority and the 24 h window instead of the coach's 7 days. Today a second trainee write is refused with `COMPLIANCE_ALREADY_RECORDED` (`meals.ts:914`, `:1208`).
- Mocks (approved, D-W14-14): `docs/design/mockups/z14-10/ios-light/` W-17c, W-17c2, W-17c3, TR-07m, TR-07m4, TR-07n…TR-07n8 show what the app needs from the API (`editableUntil`, edited marker, remove).
- The coach already edits a finished execution's RPE (`workouts.ts` near `:2273`, 7-day limit); reuse its validation and audit path, not its authority.
- Meal confirm accepts `photoIntent.mediaAssetId` at log time only (`meals.ts:797-931`); the upload flow is `files.ts:101` (create) → `:262` (PUT bytes) → `:409` (complete).

## Acceptance criteria
- [ ] `PATCH /workouts/executions/:id/feedback` (trainee, own execution, `{ rpe?: 1..10 | null, note?: string ≤ 500 | null, recordVersion }`, idempotency key; at least one field): allowed until 48 h after `completedAt`, then `422 FEEDBACK_EDIT_WINDOW_CLOSED` (static message); version mismatch `409 VERSION_CONFLICT`; writes the change log (before/after) and realtime hint like other execution edits; the coach sees the new values and an activity item. The execution read returns `feedbackEditableUntil`. Also a `sync/push` mutation type so it works offline (D-W14-22 (f) offline rule applied to the 48 h window).
- [ ] `POST /meals/logs/:id/photo` (trainee, own log, `{ mediaAssetId }`, idempotency key): asset must belong to the trainee, be `meal_photo` and ready; replaces an earlier photo (keeps history in the change log); the meal's photo requirement flips to satisfied; refused after the entry's edit window (`422 MEAL_EDIT_WINDOW_CLOSED`) and on ended relationships with the existing read-only error. Also a `sync/push` mutation type.
- [ ] Meal entries returned to the trainee (day bundle, meal reads, sync pull) carry `editableUntil` (ISO instant = trainee `loggedAt` + 24 h, or `null` when not editable: coach-logged, coach-edited, ended relationship) and `canRemove` (true only while `editableUntil` is in the future **and** the meal can still be logged: confirmation window open and day not locked). The app shows the hint and buttons from these, never its own rule.
- [ ] `PATCH /meals/logs/:id` (trainee, own entry, idempotency key, `recordVersion`): replaces outcome (`confirmed` ↔ `deviated` with portion items, food-search items or ate-out kcal), amounts, kcal, note. **Server-enforced 24 h window** from the entry's first `loggedAt`: after it `422 MEAL_EDIT_WINDOW_CLOSED`. Coach-logged entry `409 COACH_LOGGED_READ_ONLY` (existing); entry already edited by the coach `409 MEAL_EDITED_BY_COACH`; ended relationship: existing read-only error; version mismatch `409 VERSION_CONFLICT`. Sets `lastEditedByRole: "trainee"`, `lastEditedByUserId`, `lastEditedAt`, bumps `recordVersion`, writes the change log with before and after, an activity item ("Edited lunch") and the realtime hint; re-runs exception evaluation through the normal write path (D-W14-8) and never resolves an exception (only the trainer does).
- [ ] `DELETE /meals/logs/:id` (trainee, own entry, `recordVersion`, idempotency key): allowed only when `canRemove` holds, else `422 MEAL_REMOVE_NOT_ALLOWED` (window closed or the meal can no longer be logged); the meal reads as not logged again; the change log keeps the full before-image; an activity item "Removed the {meal} log"; realtime hint; exceptions re-evaluated as above.
- [ ] Both meal operations are `sync/push` mutation types. Offline rule (D-W14-22 (f)): accept when the mutation's device time is not before `loggedAt`, not later than server time + 5 min, inside the window, and the mutation arrives within 72 h of the window closing; otherwise refuse with `MEAL_EDIT_WINDOW_CLOSED` as a per-mutation verdict the app can show in sync status (friendly copy). Retries with the same mutation id are no-ops.
- [ ] Coach reads (activity feed, client day, meal panel data used by trainer web and the trainer app) expose `lastEditedByRole`, `lastEditedAt` and the previous value for trainee edits, and the removal activity item, so Z14-16 can render D-W14-23 without new endpoints.
- [ ] No migration (D-W14-18): `last_edited_*` exist; `editableUntil`/`canRemove` are computed. If a column turns out to be missing, stop per the stop conditions.
- [ ] Both added to `packages/contracts` and `packages/api-client` with friendly copy for each new code (D-W14-3).
- [ ] Query-count tests (Z14-1 style): each endpoint ≤ 4 statements in one batch where possible (meal edit and remove ≤ 6 including the change log and activity item).
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.
