## Outcome
The two API reads the mobile app makes on every trainer and trainee cold start — `GET /me` and `GET /relationships` — each answer in at most two D1 round trips, with the same response shape as today.

## Context
- FitBud Tech's staging latency check (24 Nov 2026): on every trainer/trainee cold start, the profile load and the relationships list still make several sequential D1 trips where 1–2 would do, costing about 0.1–0.2 s each from India. **D-W14-32** adds this work to W14 as an API-only task.
- Z14-1 (merged `#532` at `9e7382ff`) already cut sign-in lookup to one query and throttled `last_seen_at`. It did not own these two handlers, and they are not in `docs/qa/Z14-1/query-counts.md`.
- Z14-3 (mobile, wave A) makes the app call relationships and profile in parallel and defers push registration. This task is the server side only; it may run alongside Z14-3 (no shared files).
- Diagnosis #1 (`docs/specs/batches/W14-diagnosis.md`): the cost is D1 round trips, not query time. D1 supports `db.batch([...])` (one trip, one implicit transaction). `Promise.all` over separate statements still costs one trip each on D1; prefer `batch` (same rule as Z14-1).
- Existing helper: `apps/api/src/test-support/query-count.ts` (`installRoundTripCounter`, `measureRequest`, `loginHeaders`). Caps include auth, like `apps/api/src/routes/hot-reads.query-count.test.ts`. Do not change the helper unless a bug blocks the new tests; if you must, record it.

## Gap list
Written against `main` at `2933e0d5`. Re-check each item on the latest `main` before building; drop what is done and say so in the PR (AGENTS.md).

Mobile `AuthProvider` loads the account with `api.me()` (`packages/api-client/src/index.ts:381-382` → `GET /me`) and then `client.listRelationships({ limit: 50 })` (`index.ts:530-543` → `GET /relationships`). See `apps/mobile/src/auth/AuthProvider.tsx:492-494` and `:322`. Do not edit those files.

- **`GET /me`** (`apps/api/src/routes/auth.ts:219-269`): after the one-query actor load (`middleware/auth.ts:239` → `loadIdentityByFirebaseUid` in `auth/identity.ts:116-126`, Z14-1), the handler still runs a serial `user_identities` read for email (`auth.ts:233-237`) and, when `actor.trainerProfileId` is set, a serial `trainer_profiles` read for display name and WhatsApp (`auth.ts:240-245`). Bearer/mobile totals **3** D1 trips for a trainer and **2** for a trainee with no trainer profile.
- **`GET /relationships`** (`apps/api/src/routes/relationships.ts:53-158`): after the same one-query auth, the handler reads the page of `coaching_relationships` (`:104-113`), then `deriveOnboardingStatusForRelationships` (`:115`), then `trainer_profiles` (`:117-127`). The helper (`domain/client-status.ts:25-46`) fires three independent selects via `Promise.all` (form responses, reviews, configurations). That is still **3** D1 trips. Bearer/mobile total for a non-empty page: **6** trips (1 auth + 1 list + 3 status + 1 profiles). An empty page short-circuits the status and profile reads and is already 2.
- These counts are the mobile cold-start path (Bearer). Web cookie sessions may add one throttled `last_seen_at` write (Z14-1, at most once per 5 minutes); do not change that path.

## Decide-and-note
1. **Keep the extra reads in the handlers (recommended).** Batch or join them in `GET /me` and `GET /relationships` so every other route keeps Z14-1's one-query actor load. Do not fold email or trainer profile into `identityColumns()`.
2. **Relationships: one batch for the whole handler (recommended).** After auth, one `db.batch` (or one join) of the page of relationships, the three onboarding-status inputs, and the trainer profiles. An empty page may skip the rest. If you change `deriveOnboardingStatusForRelationships`, keep the status rule identical; `invitations.ts` and the other relationship handlers may keep calling it — do not edit `invitations.ts`.
3. **Caps use Bearer auth** via `loginHeaders` (the mobile cold start). Do not tighten or loosen the cap to include or exclude the web `last_seen_at` write.
4. **`GET /relationships/:id` (recommended):** leave it unless the shared helper change improves it at no extra cost. Say so in the PR.
