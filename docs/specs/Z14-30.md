## Outcome
A staging build that goes to TestFlight is signed and registered for the **production** push environment, so iOS pushes arrive; preview, development and ad hoc builds keep the **development** environment. One value feeds both the `aps-environment` entitlement and the `expo-notifications` plugin `mode`, so they cannot disagree.

## Context
- Z14-6 found (W14 Report, row Z14-6): `app.config.js` sets `apsEnvironment: "development"` for the staging variant, but the `staging-store` EAS profile (`distribution: store`, `APP_VARIANT=staging`) is what goes to TestFlight, and TestFlight delivers through production APNs. A token minted for development APNs will not receive pushes there. It was unverified from the agent session; Firoz decided on 25 Nov 2026 to fix it (**D-W14-35**).
- Today's resolution: `apps/mobile/app.config.js:168-190` (`VARIANTS.production|staging|development.apsEnvironment`), used at `:252-254` (entitlement) and `:272` (`["expo-notifications", { mode }]`). EAS profiles are in `apps/mobile/eas.json` (`development`, `preview`, `staging-store`, `production`). Existing config tests: `apps/mobile/app.config.test.ts:117-145`.
- This is a **native** change (entitlement): it only reaches phones in a new iOS build. Firoz's EAS pair should be built after this merges (and after the rest of the fix batch, since JS ships inside the binary; there is no OTA, `expo-updates` is not installed).

## Acceptance criteria
- [ ] `app.config.js` reads an optional `APS_ENVIRONMENT` env var. When set it must be exactly `"development"` or `"production"`, otherwise config resolution throws a message naming both allowed values. When unset the variant default applies exactly as today (production variant `production`, staging and development `development`). The one resolved value feeds the entitlement and the `expo-notifications` mode.
- [ ] A **production** variant refuses `APS_ENVIRONMENT=development` (throws): a store build can never use the sandbox.
- [ ] `eas.json`: `staging-store.env.APS_ENVIRONMENT = "production"`; `preview` and `development` set `"development"` explicitly; `production` sets `"production"`. No other field changes.
- [ ] `app.config.test.ts`: staging with `APS_ENVIRONMENT=production` gives entitlement and plugin mode `production`; staging unset and staging with `development` give `development`; production with `development` throws; a bad value throws; local `expo start` (no `APP_VARIANT`, no env) is unchanged. A test reads `eas.json` and asserts the four profile values above.
- [ ] `docs/runbooks/mobile-distribution.md`: one note under the profile table: staging-store uses production APNs (TestFlight), preview/internal/ad hoc use development; changing it needs a new iOS build; testers must install it and sign in again so a new push token is registered; to check, read `aps-environment` in the EAS build log or the built entitlements.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.

## Decide-and-note
1. **Env var over a new variant (recommended):** keep the three variants and let the EAS profile pick the APNs environment, so the staging identity (bundle id, App Group, Firebase app) is unchanged. Do not add a fourth variant.
2. **Fail loud (recommended):** an unknown `APS_ENVIRONMENT` throws at config time rather than falling back.
