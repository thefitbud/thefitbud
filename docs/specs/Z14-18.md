## Outcome
On Android, the hardware back button and the back gesture always do what the on-screen back would do: close the open sheet, or go to the screen the trainer came from, or from another tab go to Attention, and only leave the app from the Attention tab itself. On iOS, every pushed trainer screen can be swiped back from the left edge, with the previous screen visible underneath, and every pushed screen shows the same header back.

## Context
- Diagnosis #17 and #28 (iOS cause: no native stack, screens are conditional renders, so no edge swipe). **D-W14-24** (confirmed by Firoz 24 Nov 2026) (the back target for every trainer screen and sheet; this spec repeats it below). D-W14-6 (trainer online-first).
- Today the trainer app has no `BackHandler` at all (only `trainee/ActiveWorkoutScreen.tsx:479` uses one), so back falls through to Android's default and closes the app from any depth. Open `Modal` sheets already catch back through `onRequestClose`; keep that.
- Navigation is custom (no navigation library): `TrainerShell.tsx` `tab` + overlay stack (`overlayStack.ts`), local `useState` sub-screens in `ClientStatusScreen.tsx:428-499` and in `clientlog/**`. Do not introduce a navigation library in W14.
- Z14-3 keeps visited tabs mounted; going back to a tab must show it where the trainer left it (scroll position kept).
- **iOS approach (D-W14-24 c):** keep the custom navigation; render overlays as absolutely positioned layers **over** the mounted tab tree (and over the overlay below them in the stack) instead of returning them in place of it, so the previous screen is really underneath. `PushedScreen` animates in from the right (250 ms, native driver), and on iOS a pan that starts within 24 pt of the left edge drags it; release past 35 % of the width or with velocity > 500 pt/s completes `onBack`, otherwise it springs back. Vertical scroll and horizontal swipe rows inside the screen keep working (the pan only activates from the edge, `activeOffsetX`, `failOffsetY`). Android has no edge-swipe (its system back gesture is handled by `useHardwareBack`). Shared with the trainee app (Z14-25), which only consumes these components.
- Every pushed trainer screen shows `HeaderBack` at the top left (the BK-01 frame); replace the ad-hoc back controls listed in Diagnosis #28 in the screens this task owns, and add it where a pushed trainer screen has none (list every pushed screen and its back control in the PR). Screens owned by other open tasks keep their control until those tasks touch them; record which.

## Back targets (D-W14-24)
| Where the trainer is | Back does |
|---|---|
| Attention tab (no overlay, no sheet) | Leaves the app (Android default) |
| Clients, Check-ins or More tab (any segment) | Shows the Attention tab |
| Any open sheet or menu (review sheet, Remind, Resolve, note, ⋯ menus, log pick, reactivate, check-in reply, meal sheets, client picker, sign-out confirm) | Closes that sheet only; a sheet on top of another sheet closes only the top one |
| Exception, client page, check-in review, ask, session, notification settings, your profile (overlays) | The screen below it in the stack; with nothing below, the tab it was opened from (`backOverlays`, including a cold check-in → its client's page) |
| Opened from a push or deep link | The same rule: never leaves the app from an overlay; with nothing below, the Attention tab (or the tab the link set) |
| Client page → Log workout, Log meal, Log measurement, Diet day, Goal and intake | The client page |
| Client log inner view ("something different" in Log meal) | The log screen's main view |
| A log screen with unsaved input | The same discard question as its on-screen Back; if it has none, "Discard this log?" with Discard / Keep editing |
| The profile's inline note form (until Z14-24 replaces it) | Closes the form; if text was typed, "Discard this note?" Discard / Keep writing |

## Acceptance criteria
- [ ] `useHardwareBack(handler, enabled = true)` wraps `BackHandler.addEventListener("hardwareBackPress")`; the most recently mounted enabled handler runs first; returning `true` consumes the press. No-op on iOS and web.
- [ ] `TrainerShell` registers one handler implementing the tab and overlay rows of the table, through the existing `goBack()`/`backOverlays` (no second back stack).
- [ ] `ClientStatusScreen` and `clientlog/**` register handlers for their inner views and unsaved input as in the table; the on-screen Back and the hardware back call the same function.
- [ ] Every `Modal` in `apps/mobile/src/trainer/**` has `onRequestClose` that closes only itself (add where missing; list the ones checked in the PR).
- [ ] No back press ever leaves the app while an overlay, sub-screen or sheet is showing.
- [ ] iOS: on every pushed trainer screen (overlays and client-page sub-screens) a left-edge swipe shows the previous screen underneath and completes or cancels as above; the tab bar and the screen below keep their scroll position; VoiceOver users get the same result from the `HeaderBack` button and the two-finger scrub (`accessibilityEscape` / `onAccessibilityEscape` calls `onBack`).
- [ ] `HeaderBack`: iOS chevron with the parent's short name when known ("Attention", "Rohan"), otherwise "Back"; Android a ← icon with label "Back" for screen readers; 44×44 pt minimum target; used by every pushed trainer screen this task owns.
- [ ] Overlays render over the mounted tabs; a push or deep link still opens on top of the right tab; capture mode (`registerTrainerCaptureNav`) still works.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.
