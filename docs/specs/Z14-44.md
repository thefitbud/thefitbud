## Outcome
A live hint about a trainee's meal or workout no longer reloads the whole plan and sync as if everything had changed. The day (or days) already on the phone stay on screen and are refreshed underneath; a plan hint still reloads the plan, and a notification hint still refreshes the unread count. Realtime events stay hints, not CRUD payloads.

## Context
- FitBud Tech's 25 Nov 2026 audit: "trainee live updates still trigger a refetch" instead of updating the cached day. This is a small leftover after the server-side latency work and Z14-2's day cache.
- On `main` at `ddd48f22`, `TraineeShell` calls `useRealtimeHints(api, relationship.id, () => { void loadEffectivePlan(); void refreshUnread(); })`. `loadEffectivePlan` runs `sync.pullAndApply()` and `api.getEffectivePlan` on **every** hint, including a meal or workout change. The event itself is ignored.
- Realtime events are compact by design (`packages/contracts/src/realtime.ts`): `eventType`, `entityType`, `entityId`, `coachingRelationshipId`, `serverVersion`, `occurredAt`. They do not carry meal or workout fields, so the client cannot patch a log line from the socket. "Update the cached day" means: keep showing the cached day, and refetch only what that event could have changed — not a full plan pull on a meal hint, and not a wipe of every date.
- Event types on the contract: `effective_plan_changed`, `workout_execution_changed`, `meal_compliance_changed`, `checkin_submitted`, `checkin_reviewed`, `exception_created`, `exception_acknowledged`, `exception_resolved`, `exception_changed`.
- **D-W14-39**. Z14-41 (wave B) also edits `TraineeShell.tsx`; this task starts only after that PR has merged. Re-check the hint callback on that `main` and keep the launch-resume wiring.

## Acceptance criteria
- [ ] `meal_compliance_changed` and `workout_execution_changed`: do **not** call `loadEffectivePlan`. Mark the already-cached day views for this relationship stale and refetch those (today and any other date already in the cache). The day stays on screen from the cache while that refetch runs (same stale-while-refresh idea as `invalidateRelationshipDayData`, but do not delete every meals/workouts/week key for all dates if a narrower helper will do). If the event's `entityId` can be mapped to a cached day cheaply, only that day is refetched; if it cannot (events have no date field), refetch the days already cached for this relationship, not a cold fetch of an unbounded range.
- [ ] `effective_plan_changed`: reload the plan (today's `loadEffectivePlan` is appropriate) and mark cached days stale so Today/Diet/Workout pick up the new plan underneath.
- [ ] Check-in and exception hints: refresh unread if that is still the right place; do not reload the plan or all days unless a cached progress/check-in view needs a quiet refresh. Say what you chose.
- [ ] Offline, or when the socket is down, REST and sync stay correct (the hook already treats socket errors as non-fatal). A hint that arrives while offline is dropped or applied later by the existing pull — do not invent a new outbox for hints.
- [ ] No raw event payloads, ids or error codes on screen (D-W14-3). No new user-visible copy.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` pass.

## Decide-and-note
1. **Mapping entityId to a day (recommended):** do not add a new API. If the id is already in the day cache, use that day; otherwise stale-and-refetch the relationship's already-cached days. Record which you could do.
2. **Where the mapping lives (recommended):** a small `realtimeDayUpdate.ts` helper called from the shell's `onHint`, so the hook stays a thin subscriber.
